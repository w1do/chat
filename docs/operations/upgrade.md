# Обновление

Статус: in progress

Релизы следуют SemVer; образы закреплены по версиям (`CHAT_API_IMAGE`,
`CHAT_WEB_IMAGE` в `.env`).

## Процедура

1. Прочитайте upgrade notes релиза (GitHub Release).
2. Сделайте backup БД и файлов хранилища (см. backup-restore.md).
3. Обновите версии образов в `.env`.
4. Примените:
   ```bash
   docker compose --env-file .env -f compose.prod.yaml pull
   docker compose --env-file .env -f compose.prod.yaml up -d
   docker compose -p chat exec api php artisan migrate --force
   ```
5. Graceful reload (код в памяти long-running процессов):
   ```bash
   ./tools/chat deploy reload
   ```
6. Проверьте `/up` и `/api/v1/readiness`.

## Откат

Верните предыдущие версии образов в `.env` и повторите `up -d`. Миграции
вперёд-несовместимого отката не имеют — восстанавливайте БД из backup
(post-release миграции пишутся только forward, CLAUDE.md §12).

Автоматические миграции при старте контейнера выключены по умолчанию
(`AUTO_MIGRATE=false` в entrypoint) — включайте осознанно.

## Обновление до версии с авторизацией по токену

Клиент перешёл с cookie-сессии на bearer-токен Sanctum (ADR-012). Обновление
обратной совместимости не имеет: старый клиент не умеет заголовок
`Authorization`, новый — cookie.

**Все входят заново один раз.** Прежние cookie-сессии больше не признаются;
после обновления каждый вводит логин и пароль. Это ожидаемое поведение
обновления, а не сбой.

Что нужно сделать:

1. Обновить образы `api` и `web` **одним** релизом — промежуточного
   совместимого состояния нет.
2. Выполнить graceful reload (шаг 5 процедуры выше): иначе worker'ы Octane
   продолжат держать прежнюю конфигурацию middleware.
3. Из `.env` можно удалить `SANCTUM_STATEFUL_DOMAINS`, `SESSION_SECURE_COOKIE`
   и `AUTH_BROWSER_TOKEN_*`, а также `AUTH_SILENT_RECOVERY`: их больше никто не
   читает. Оставленные значения безвредны.

Что изменилось в контракте API:

- ответы `POST /auth/login` и `POST /auth/register` получили поле `token` —
  plaintext-токен без срока истечения; клиент хранит его сам;
- `POST /invites/{token}/accept` возвращает `token`, когда создаёт аккаунт
  гостю: своего пароля у такого аккаунта нет;
- поле `remember` из `POST /auth/login` **удалено**. Клиент, который его
  присылает, не ломается — поле просто игнорируется;
- схема безопасности в OpenAPI: `bearerAuth` вместо `sanctumCookie`;
- `GET /sanctum/csrf-cookie` **удалён** (`sanctum.routes => false`): вместе с
  ним из схемы ушёл и CSRF-handshake.

Миграций базы обновление не добавляет: таблица `personal_access_tokens` уже
есть. Ранее выданные browser-токены остаются в ней строками, перестают
приходить в запросах и доходят до неактуальности своим `expires_at` — отдельная
уборка не нужна.

Откат — возврат предыдущих образов: схема данных не менялась, поэтому откат
безопасен; людям придётся войти ещё раз, теперь уже в cookie-схему.

## Обновление до версии с обязательным хранилищем

Объектное хранилище стало обязательным компонентом (ADR-011). Установка,
поднятая раньше без профиля `s3`, требует одного дополнительного шага.

1. Добавьте в `.env` ключи хранилища (пароль — не короче восьми символов):
   ```
   S3_ACCESS_KEY_ID=chat
   S3_SECRET_ACCESS_KEY=<свой пароль>
   ```
   Своё S3-совместимое хранилище вместо встроенного — добавьте `S3_ENDPOINT`.
2. Поднимите стек обычной командой: сервис хранилища появится сам, бакет
   создастся при старте.
3. Убедитесь, что всё на месте:
   ```bash
   curl https://<домен>/api/v1/readiness    # storage: ok
   ./tools/chat smoke storage
   ```

Без этих переменных стек не поднимется, а не сломается позже при первой
загрузке файла: `compose.prod.yaml` требует их явно.
