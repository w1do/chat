# ADR-012: Bearer-токен Sanctum как единственная авторизация клиента

- Статус: accepted
- Дата: 2026-08-28
- Заменяет: [ADR-005](ADR-005-sanctum-spa-auth.md)

## Контекст

ADR-005 выбрал cookie-схему Sanctum: session-cookie плюс CSRF-handshake. В
реальной self-hosted установке она не заработала.

Стек отдаётся по `http` (`APP_URL: http://localhost`,
`SESSION_SECURE_COOKIE=false`), а cookie браузерного токена называлась
`__Host-chat_browser_token`: браузер обязан отбросить cookie с этим префиксом,
если у неё нет атрибута `Secure`. Cookie до сервера не возвращалась,
авторизация оставалась сессионной, и через `SESSION_LIFETIME` (по умолчанию 120
минут) человек получал `401` и форму входа. Владелец продукта потребовал убрать
браузерную схему целиком.

Дополнительные ограничения решения:

- клиент и API живут за одним reverse proxy, но это перестаёт быть
  требованием;
- таблица `personal_access_tokens` уже есть, `sanctum.expiration` уже `null`;
- Octane переиспользует worker между запросами — identity нельзя кэшировать;
- аватарки, фото комнат и вложения отдаются защищёнными эндпоинтами и рисуются
  в интерфейсе как изображения; service worker кеширует их по адресу.

## Решение

Единственный способ авторизации клиента — personal access token Sanctum без
срока истечения.

- `POST /auth/login`, `POST /auth/register` и `POST /invites/{token}/accept`
  (когда создаётся аккаунт гостя) возвращают plaintext-токен в теле ответа
  рядом с пользователем. Токен создаётся `createToken('client', ['*'])` без
  `expires_at` и действует, пока его не отозвали.
- Клиент хранит токен в `localStorage` и отправляет заголовком
  `Authorization: Bearer <token>` в каждый запрос к API и к
  `/broadcasting/auth`. Восстановление входа при старте — `GET /me`.
- Сессионный стек снят целиком: `statefulApi()`, `sanctum.stateful`,
  `X-XSRF-TOKEN` и `credentials: 'include'` в схеме отсутствуют, маршрут
  `GET /sanctum/csrf-cookie` выключен (`sanctum.routes => false`), а
  stateful-middleware Sanctum убраны из конфигурации — их читал только
  `statefulApi()`.
  `sanctum.guard` — пустой массив, иначе Sanctum молча пробовал бы
  session-guard `web` при отсутствии токена. Группа `web` остаётся только у
  Horizon-дашборда.
- Защищённые файлы (аватарки, фото комнат, миниатюры и оригиналы вложений)
  запрашиваются авторизованным `fetch` и показываются из `blob:`-адреса
  (`<AuthorizedImage>` в `@vendor/ui`). Адреса не меняются, поэтому кеш
  изображений service worker'а продолжает работать; `cache.match` получает
  `{ ignoreVary: true }`.
- Отзыв: выход отзывает токен текущего устройства, сброс пароля — все токены
  человека, смена пароля в настройках — все, кроме токена самого запроса.
- `401` по защищённому запросу после состоявшегося входа означает отозванный
  токен: клиент один раз стирает токен, гасит сокет, чистит кеш изображений и
  уходит на `/login`. Автоматических попыток восстановления нет.

## Альтернативы

- **Оставить cookie-схему и починить её** — потребовало бы обязательного TLS в
  каждой установке (или переименования cookie с потерей защиты `__Host-`) и
  всё равно сохраняло бы `SESSION_LIFETIME` как срок жизни входа. Отвергнуто:
  ровно эту проблему change и решает.
- **Короткий токен плюс refresh** — возвращает ту же проблему (человека просят
  войти заново) и требует хранить второй секрет. Отвергнуто.
- **Токен вне JS (httpOnly cookie с токеном)** — это и есть отброшенная
  `__Host-` cookie; в установке по `http` она не доезжает.
- **Подписанные ссылки на файлы вместо авторизованного `fetch`** — подпись
  подменяет проверку прав знанием адреса (вложение из чужой комнаты открылось
  бы по пересланной ссылке), а меняющийся `expires` в query ломает ключ кеша
  service worker'а. Отвергнуто.
- **Подстановка заголовка в service worker** — worker живёт только в secure
  context; установка по `http` — ровно тот случай, который сломал cookie.

## Последствия

- **Принятый риск: XSS крадёт бессрочный токен.** Решение владельца продукта.
  Смягчения: токен лежит по одному известному ключу и стирается при `401` и
  выходе; сброс пароля отзывает все токены и даёт способ прекратить доступ;
  пользовательский текст по-прежнему не рендерится как HTML. Риск записан и в
  [threat model](../security/threat-model.md).
- **Токен не истекает.** Украденный или забытый на чужом устройстве токен
  действует, пока его не отозвали; списка активных устройств в MVP нет.
- **Разовый разлогин при обновлении.** Cookie-сессии перестают признаваться —
  все входят заново один раз ([upgrade](../operations/upgrade.md)).
- **BREAKING в контракте:** поле `remember` уходит из `/auth/login`; ответы
  входа и регистрации получают поле `token`; `sanctumCookie` в OpenAPI заменена
  на `bearerAuth`.
- Из окружения уходят `SANCTUM_STATEFUL_DOMAINS`, `SESSION_SECURE_COOKIE` и
  `AUTH_BROWSER_TOKEN_*`; оставленные в чужом `.env` значения безвредны — их
  больше никто не читает.
- Horizon-дашборд остаётся за группой `web` и gate `viewHorizon`; браузерной
  сессии в схеме больше нет, поэтому доступ к нему открывается отдельно
  (туннель, отдельный доступ оператора) — к контракту чата это не относится.
- Мульти-домен и сторонние клиенты больше не требуют same-site: заголовок
  работает откуда угодно, ограничение остаётся за CORS-allowlist.

## Критерии пересмотра

- Появление списка активных устройств или требования отзывать доступ выборочно
  → срок жизни токена и ротация.
- Подтверждённый инцидент кражи токена через XSS → пересмотр хранения
  (httpOnly-cookie при обязательном TLS) новым ADR.
- Требование SSO/OIDC у клиентов self-hosted.
- Появление внешнего API-потребителя → отдельные abilities вместо `*`.
