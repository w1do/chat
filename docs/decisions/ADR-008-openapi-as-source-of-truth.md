# ADR-008: OpenAPI как источник истины для frontend-клиента

- Статус: accepted
- Дата: 2026-08-24

## Контекст

Инструкция требует OpenAPI 3.1 как единственный публичный контракт HTTP API и
генерируемый из него TypeScript-клиент (CLAUDE.md §3). Монорепозиторий
package-first: описания endpoints принадлежат backend-пакетам, но клиент
генерируется из контракта конкретного приложения.

## Решение

1. Каждый backend-пакет держит свои фрагменты в
   `packages/backend/<pkg>/openapi/{paths,schemas}/*.yaml`
   (имя файла схемы = имя в `components.schemas`).
2. Приложение собирает итоговую спецификацию:
   `apps/chat-api/openapi/build.php` мержит `openapi.base.yaml` (info, servers,
   securitySchemes, общие responses, схема `ApiError`) с фрагментами
   подключённых пакетов в **коммитящийся** артефакт `openapi/dist/openapi.json`.
   Конфликты путей/схем между пакетами — ошибка сборки.
3. `./tools/chat openapi validate` пересобирает спецификацию и падает при
   расхождении с закоммиченным dist (CI-гейт «нет незакоммиченного диффа»).
4. TypeScript-типы генерируются из dist инструментом `openapi-typescript` в
   `packages/frontend/api-client/src/generated/` (`./tools/chat client generate`);
   ручные правки в `generated/**` запрещены. Обёртка `src/{client,errors}.ts`
   реализует envelope, `trace_id` и обработку 401/419/429 и пишется вручную.
5. Порядок изменения API: код + фрагменты пакета → rebuild dist → regenerate
   client → contract/feature тесты → документация. Всё в одном изменении.

## Альтернативы

- **Генерация OpenAPI из аннотаций кода** (swagger-php и т.п.) — отвергнуто:
  контракт становится побочным продуктом реализации, ломающие изменения
  проскальзывают незамеченными; contract-first держит diff контракта явным.
- **Ручной TypeScript-клиент** — отвергнуто: дрейф типов от контракта,
  двойная работа.
- **Полноразмерные генераторы клиентов (openapi-generator, orval)** —
  отвергнуто на MVP: тяжёлая java-цепочка или лишний рантайм; `openapi-typescript`
  генерирует только типы, обёртка остаётся тонкой и контролируемой.

## Последствия

- dist-файл в git: ревью изменений API происходит по диффу спецификации.
- CI обязан запускать `openapi validate` и `client generate` с проверкой
  чистоты рабочего дерева (этап 12).
- Real-time события версионируются отдельно JSON Schema в `packages/contracts`
  (см. `docs/api/realtime-events.md`); OpenAPI покрывает только HTTP.

## Критерии пересмотра

- Появление второго backend-приложения с собственным контрактом → выделение
  общей сборочной утилиты.
- Потребность в runtime-валидации ответов или SDK для внешних потребителей →
  пересмотр выбора генератора.
