# ADR-004: Лёгкий CQRS без event sourcing

- Статус: accepted
- Дата: 2026-08-24

## Контекст

Инструкция (CLAUDE.md §6) требует разделения классов изменения и чтения, но
запрещает переусложнение: одна PostgreSQL, без event sourcing и асинхронных
проекций.

## Решение

- Мутации — `VerbNounCommand` (readonly DTO) + один handler на use case;
  handler координирует транзакцию, row-lock и доменные объекты; события/jobs —
  после commit.
- Чтение — `Get/List…Query` + handler; для простых списков handler использует
  Eloquent/Builder напрямую (`ListRoomsHandler`, `ListMessagesHandler`).
- Вызов — обычный constructor injection в контроллере: Request → Command/Query
  → Handler → DTO → Resource. Никакого command bus/mediator: пока прямой DI
  ясен, шина — лишний слой.
- Одна база, одна схема; курсоры и счётчики читаются из тех же таблиц.
- Команды возвращают компактный result DTO (`RoomData`, `MessageData`).

## Альтернативы

- **Command bus (например, средствами Laravel Bus)** — отвергнуто: не даёт
  ценности при синхронных handlers, усложняет трассировку.
- **Event sourcing / проекции** — явно вне MVP по инструкции.
- **Репозитории поверх каждого Eloquent-запроса** — отвергнуто: интерфейс
  вводится только при реальной сменяемости хранилища (пример:
  `MessageSanitizer`, `PresenceRegistry` — контракты там, где есть смена
  реализации).

## Последствия

- Слои повторяемы во всех пакетах (identity, chat, далее notifications/ai);
  тестируются handler'ы напрямую и через HTTP.
- При появлении измеримой потребности (асинхронные команды, outbox) решение
  пересматривается новым ADR.

## Критерии пересмотра

- Появление длительных команд, требующих очереди/статусов выполнения.
- Второе хранилище чтения (кроме восстановимого поискового индекса Typesense).
