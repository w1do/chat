# Пересказ приложенного документа (`@ai` в ответе)

Статус: implemented

## Сценарии

- Человек отвечает на сообщение, к которому приложен **один** документ
  (`.pdf`, `.docx`, `.txt`), и пишет в ответе `@ai`. Панель ввода подсказывает
  это словами, как только начат ответ на документ.
- Отправка такого ответа не публикует его в комнату: уходит запрос пересказа,
  а над лентой идёт ход обработки.
- Готовый пересказ (500–800 символов) показывается **только** запросившему —
  листом с вступлением «Вот что:» и вопросом «Отправить пересказ в чат?».
- «Отправить» публикует пересказ обычным сообщением от имени человека, ответом
  на исходный документ. «Не отправлять» закрывает лист, в комнате не остаётся
  ничего.
- Отказ (нет текстового слоя, таймаут, выключенный помощник) объясняется
  словами; переписка при этом работает как обычно.
- После переподключения состояние операции и черновик читаются по HTTP —
  пропущенное real-time событие ничего не теряет.

## Права и ограничения

| Ограничение | Значение по умолчанию | Настройка |
|---|---|---|
| Виды документов | `.pdf`, `.docx`, `.txt` | `ai.file_summary.types` |
| Размер документа | 5 МБ | `AI_SUMMARY_MAX_FILE_KB` |
| Текста поставщику | 24 000 символов | `AI_SUMMARY_MAX_DOCUMENT_CHARS` |
| Длина пересказа | 500–800 символов | `AI_SUMMARY_MIN_LENGTH`, `AI_SUMMARY_MAX_LENGTH` |
| Таймаут поставщика | 40 с | `AI_SUMMARY_TIMEOUT_SECONDS` |
| Квота на пользователя | 20/час | `AI_SUMMARY_PER_USER_HOURLY` |
| Квота на установку | 200/час | `AI_SUMMARY_PER_INSTALL_HOURLY` |
| Очередь | `ai` (группа Horizon `supervisor-ai`) | `AI_SUMMARY_QUEUE` |
| Жизнь черновика | 24 ч | `AI_SUMMARY_DRAFT_TTL_HOURS` |

Пересказ доступен только участнику комнаты, которому видно исходное сообщение:
посторонний получает 403, а в чужой личной переписке — 404, как и везде.
Помощник целиком выключается администратором (`AI_ENABLED=false`): endpoint
отвечает 503, подсказка не показывается, ответы отправляются как обычно.

Цепочка таймаутов (CLAUDE.md §14): поставщик 40 с < `timeout` задания 50 с <
`timeout` супервизора Horizon 60 с < `retry_after` очереди 90 с.

## API и события

| Метод | Адрес | Ответ |
|---|---|---|
| POST | `/api/v1/ai/file-summaries` | `202` — операция принята; `200` — повтор с тем же `idempotency_key` |
| GET | `/api/v1/ai/file-summaries/{id}` | `200` — состояние и черновик (только автору запроса) |
| POST | `/api/v1/ai/file-summaries/{id}/publish` | `201` — опубликовано; `409` — не готово, просрочено или уже опубликовано |

Тело запуска: `message_id`, `body` (обязан содержать `@ai`), необязательные
`idempotency_key` и `locale`. Повтор с тем же ключом возвращает ту же операцию
и не ставит второе задание.

Событие `ai.file_summary.updated.v1` уходит на приватный канал
`user.{userId}` автора запроса и несёт только `{id, status, progress,
error_code}` — сам черновик по каналу не передаётся, его читают запросом
(`docs/api/realtime-events.md`).

## Приватность

Наружу уходит только извлечённый текст документа и системный промпт; ни
истории комнаты, ни имени файла, ни данных отправителя. Черновик хранится в
`ai_file_summaries` и виден только автору запроса до публикации. В журнал
уходят код категории отказа и класс ошибки — ни текста документа, ни
пересказа; в `ai_requests` и `audit_logs` — операция, комната, сообщение,
поставщик, модель, MIME, размер, токены, стоимость, длительность и статус.
Подробности — ADR-006.

## Реализация

- Backend: `packages/backend/ai` — контракты `FileSummaryProvider`,
  `SummarySource`, `SummaryPublisher`, `TextExtractor`, `Metrics`;
  `PolzaFileSummaryProvider`, `NullFileSummaryProvider`,
  `FakeFileSummaryProvider`; `DocumentTextExtractor` (PDF/DOCX/TXT без внешних
  зависимостей); `SummarizeFileHandler`, `SummarizeFileJob` (уникальный ключ,
  backoff, `failed()` → аудит), `PublishFileSummaryHandler`,
  `GetFileSummaryHandler`; окно длины держит `SummaryText`.
- Связка с перепиской — в composition root: `App\Ai\ChatSummarySource`
  (право на сообщение, единственный документ, язык переписки) и
  `App\Ai\ChatSummaryPublisher` (обычная отправка сообщения от имени
  человека). Пакет `ai` моделей чата не знает (STRUCTURE.md §2).
- Frontend: `useFileSummary` и `FileSummarySheet` в `packages/frontend/chat`,
  распознавание `@ai` и подсказка в `ChatScreen`, личный канал через
  `EchoAdapter.subscribeUser`.

## Проверки

- `./tools/chat test ai` — 70 тестов пакета: окно длины на границах, разбор
  PDF/DOCX/TXT и отказ сканам, триггер отдельным словом, идемпотентность,
  квоты, отказ и таймаут поставщика, приватность черновика, публикация и
  повторная публикация, метрики, журнал без приватного текста, отказ загрузки
  при пустом ключе в разработке;
- `./tools/chat test api tests/Integration/AiFileSummaryTest.php` — сквозной
  путь на живых моделях чата: 403 постороннему, 422 не-документу, публикация
  обычным сообщением с событием комнаты, аудит без текста документа, работа
  чата при недоступном поставщике;
- `./tools/chat test api tests/Contract` — схема события и его payload;
- `./tools/chat web test chat` — распознавание `@ai` и документа, перехват
  отправки, лист с черновиком и подтверждением;
- `./tools/chat openapi validate` — контракт трёх адресов;
- `./tools/chat smoke polza` — необязательная проверка против настоящего
  Polza (нужен `AI_API_KEY`, в обычном CI пропускается).

Запуск E2E: `./tools/chat e2e ai-file-summary` — два браузера, документ,
ответ с `@ai`, черновик и публикация. Сценарий подстраивается под настройки
стека: при выключенном помощнике проверяет, что подсказки нет и ответ уходит
обычным сообщением; при `CHAT_AI_ENABLED=true` без ключа поставщика — что
просьба к помощнику не публикуется, отказ объясняется словами и переписка
продолжает работать; при `E2E_AI_ENABLED=true` с настоящим ключом — весь путь
до публикации пересказа.

Что уже прогонялось: обе конфигурации без ключа поставщика (зелёные на
собранных образах). Успешный пересказ настоящим Polza в E2E не выполнялся —
для него нужен `AI_API_KEY`; логика успеха покрыта package- и
integration-тестами с фейковым поставщиком.
