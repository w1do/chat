# Аутентификация

Статус: verified (E2E `./tools/chat e2e auth`)

## Сценарии

- Регистрация: логин (3–64 символа, латиница/цифры/`._-`) и пароль не короче
  того, что требует установка (`PASSWORD_MIN_LENGTH`, по умолчанию один символ).
  Почта не запрашивается; отображаемое имя по умолчанию совпадает с логином.
  Вход выдаётся сразу — вместе с ответом приходит токен доступа.
- Вход по логину и паролю. «Запомнить меня» нет: токен и так бессрочен.
- Выход отзывает токен текущего устройства; на остальных человек остаётся
  вошедшим.
- Восстановление пароля по почте — только для аккаунтов, где почта указана
  в настройках; ответ одинаков для любого адреса, интерфейс объясняет
  требование почты вместо мнимой «отправки письма».
- Почта и пароль меняются в настройках (`PATCH /me/email`, `PATCH /me/password`;
  смена пароля требует текущий).

## Реализация

- Backend: `packages/backend/identity` (commands/handlers Register, Login,
  Logout, RequestPasswordReset, ResetPassword; bearer-токен Sanctum — ADR-012).
- Приложение: маршруты `/api/v1/auth/*`, `App\Models\User` через
  `config('identity.user_model')`, CORS и trusted proxies в `apps/chat-api`
  (`config/cors.php`, `bootstrap/app.php`); `sanctum.guard` пуст, session-стека
  у API нет.
- Frontend: `packages/frontend/identity` — `LoginForm`, `RegisterForm`,
  `RecoveryForm`, guard-хуки `useAuth`; страницы и route guards в `chat-web`.

## Права и лимиты

- Rate limits: login 5/мин (логин+IP), register 10/мин (IP), reset и смена
  почты/пароля 5/мин (IP).
- Логин уникален на уровне БД; почта уникальна при наличии значения.
- CSRF в схеме нет: API определяет человека только по заголовку
  `Authorization`, cookie на результат не влияет. Ошибки — в едином envelope.

## API

`/auth/register`, `/auth/login`, `/auth/logout`, `/auth/forgot-password`,
`/auth/reset-password`, `/me/email`, `/me/password` —
см. `apps/chat-api/openapi/dist/openapi.json`.

## Токен доступа

Вход отдаёт **personal access token Sanctum без срока истечения** (ADR-012).
Токен приходит в теле ответа `/auth/login`, `/auth/register` и — для гостя,
которому по приглашению создали аккаунт, — `/invites/{token}/accept`.

- клиент хранит токен в `localStorage['chat.auth-token']` и отправляет его
  заголовком `Authorization: Bearer <token>` в каждый запрос к API и к
  `/broadcasting/auth`;
- восстановление входа при старте — один `GET /me` с этим заголовком. Ни
  сессия на сервере, ни Redis, ни cookie в этом не участвуют, поэтому вход
  переживает и перезапуск браузера, и перезапуск контейнера `api`;
- каждый вход создаёт **отдельный** токен: вход со второго устройства не
  трогает первое;
- если `localStorage` недоступен (приватный режим, запрет политики),
  приложение работает в пределах вкладки и после её закрытия просит вход
  заново — вместо того чтобы упасть;
- выход в одной вкладке гасит остальные: значение общее на браузер, и вкладки
  синхронизируются событием `storage`.

Защищённые файлы браузер не умеет запрашивать сам — к `<img src>` он не
приложит заголовок. Аватарки, фото комнат, миниатюры и оригиналы вложений
грузятся авторизованным `fetch` и показываются из `blob:`-адреса
(`<AuthorizedImage>` в `@vendor/ui`). Адрес файла не меняется, поэтому кеш
изображений service worker'а продолжает работать. Скачивание файла — тоже
авторизованный запрос, а не обычная ссылка.

**Принятый риск.** Токен в `localStorage` доступен JS, поэтому XSS крадёт вход
целиком, и токен не истекает сам. Решение принято владельцем продукта и
записано в ADR-012 и в threat model вместе со смягчениями.

## Отзыв токена

| Действие | Что отзывается |
|---|---|
| Выход | только токен текущего устройства |
| Сброс пароля по письму | все токены человека |
| Смена пароля в настройках | все, кроме токена самого запроса |

Повторный выход недействительным токеном отвечает `401`, а не ошибкой сервера.
Отозванный токен не авторизует ни HTTP-запрос, ни `/broadcasting/auth`.

## 401 после входа

`401` по защищённому запросу при сохранённом токене означает одно: токен
отозван. Восстанавливать нечего, и клиент не пытается — «тихого восстановления»
и экрана «Сессия истекла» больше нет.

- **до входа** ответ 401 означает «человек не представился». Поведение прежнее:
  route guard уводит на `/login`, а экраны `/login` и `/invite/{token}` остаются
  на месте — там 401 ожидаем;
- **после состоявшегося входа** первый 401 один раз переводит клиент в «вход
  недействителен»: токен стирается, висящие запросы снимаются, сокет Reverb
  замолкает, кеш изображений на устройстве очищается, и приложение уходит на
  `/login` полной перезагрузкой.

Сколько бы запросов ни ответило 401 разом, переход происходит один раз — отсюда
и отсутствие мигания. Пока состояние не разрешено, защищённые запросы
обрываются в клиенте и **не уходят в сеть**; исключение — публичные пути
`/auth/*` и `/invites/*`. Токена нет вовсе — тот же запрет: защищённый запрос
не отправляется.

## Требование к паролю

Минимальная длина задаётся установкой переменной `PASSWORD_MIN_LENGTH` и
действует одинаково при регистрации, смене и восстановлении пароля. Сервер
берёт её из `identity.password.min_length`, интерфейс — из `/config.json`,
который web-контейнер рендерит на старте. Значение одно на обоих концах:
**форма не бывает строже сервера**, и число называется прямо в подсказке под
полем и в тексте ошибки. Пересобирать образ ради смены требования не нужно —
достаточно перезапуска.

## Показ введённого пароля

У каждого поля пароля есть переключатель показа — при входе, регистрации и
смене пароля. По умолчанию пароль скрыт; показ включает сам человек и только
для того поля, где нажал. Имя кнопки называет поле («Показать пароль: Новый
пароль»), потому что в форме смены пароля таких полей два.

Переключатель — обычная кнопка в порядке табуляции: она объявляет состояние
через `aria-pressed` и не отправляет форму. Нажатие не отбирает фокус у поля
(иначе на телефоне схлопывается клавиатура) и не сдвигает курсор.

Полям пароля выключены автозаглавные буквы, автокоррекция и проверка
орфографии: на открытом поле система иначе молча правит набранное, а проверка
орфографии отправляет видимый текст на сторонний сервис.

При отправке формы поле возвращается в скрытый вид — синхронно, до того как
браузер оценит форму, иначе он перестаёт предлагать сохранить пароль.
Отклонённая отправка оставляет поле скрытым: значение сохраняется, и показ
можно включить снова.

## Сообщения об ошибках

Ошибки форм пишутся на языке интерфейса и объясняют, что не так. Служебные
коды в поле ошибки — дефект: до этого изменения человек, вводя короткий
пароль, видел `validation.password_min`. Отдельный тест обходит схемы форм в
`packages/frontend/identity` и `packages/frontend/chat` и падает, если
сообщение выглядит как ключ перевода.

## Edge cases

- Неверные учётные данные → 401 `unauthenticated`; ответ одинаков для
  существующего и несуществующего логина.
- Занятый логин → 422 с ошибкой на поле `login`.
- Аккаунт без почты писем восстановления не получает.
- Занятая чужая почта при сохранении в настройках → 422.
- Неверный текущий пароль при смене → 422 на поле `current_password`.
- Неверный/истёкший токен сброса → 422.
- Показ пароля включён, форма отправлена → поле скрывается до отправки, чтобы
  браузер по-прежнему предлагал сохранить пароль.
- Пароль короче требования установки → 422 на поле `password`; форма не
  отправляет такой запрос и объясняет нужную длину.
- Токен отозван посреди работы → токен стирается, сокет гаснет, приложение
  уходит на `/login`; повторы запросов прекращаются.
- Несколько запросов ответили 401 разом → один переход, а не мигание.
- Вкладка провисела в фоне и вернулась → токен по-прежнему годен, и запрос
  проходит: срока жизни у входа больше нет.
- Изображение или файл не загрузились → на месте картинки обычная замена
  (буква имени, эмодзи, заглушка), повторов нет.

## Критерии приёмки / проверки

- `./tools/chat test identity` — package unit+feature (19 тестов);
- `./tools/chat test api tests/Integration` — happy path, invalid credentials,
  rate limit, мутация без CSRF-handshake, отсутствие fallback на session-guard,
  CORS allowlist и preflight с заголовком `Authorization`;
- `./tools/chat test api tests/Octane` + `./tools/chat smoke octane` —
  отсутствие утечки identity между запросами одного FrankenPHP worker'а;
- `./tools/chat web test identity` — формы входа, регистрации, восстановления,
  почты и пароля, требование к паролю на двух значениях установки, сторож
  против служебных кодов в сообщениях и переключатель показа пароля;
- `./tools/chat e2e auth` — показ пароля в браузере: включение не отправляет
  форму, отправка возвращает поле в скрытый вид;
- `./tools/chat web test api-client` — состав заголовков запроса, отсутствие
  cookie, CSRF-заголовка и handshake;
- `./tools/chat web test` — хранилище токена (`tests/AuthToken.test.tsx`),
  перехват 401, короткое замыкание защищённых запросов, отключённый повтор,
  гашение сокета и уход на `/login` (`tests/SessionExpiry.test.tsx`) и сценарий
  целиком — отзыв токена посреди работы → уход на вход → работа после
  повторного входа (`tests/SessionExpiryFlow.test.tsx`).

Запуск E2E: `./tools/chat e2e auth` — регистрация по логину, сохранение входа
после перезагрузки страницы и в новом контексте браузера с тем же хранилищем,
выход и отказ при неверном пароле.
