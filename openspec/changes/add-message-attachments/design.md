## Context

Мотивация — в `proposal.md`, требования — в `specs/`. Ниже то, что определяет
подход; проверено по коду.

- Вложений в продукте нет вовсе: `messages.body` — `text not null`,
  `SendMessageRequest` требует `body`, в `MessageResource` файлов нет.
- Обязательное объектное хранилище, закрытый диск с префиксом `uploads/`,
  библиотека медиа, отдельная очередь конверсий, webp как формат производных
  и расширение обработки изображений в образе приходят из
  `add-object-storage-foundation`. Здесь это предпосылка, а не работа.
- Отправка идемпотентна по `Idempotency-Key` (ключ на пользователя, сутки),
  тело санируется `MessageSanitizer`, событие уходит после commit.
- Пакет `chat` не знает класс пользователя приложения и берёт его через
  конфигурацию auth-провайдера; та же дисциплина нужна и медиа.

## Goals / Non-Goals

**Goals:**

- Приложить файл так же просто, как написать текст.
- Файлы лежат в одном месте — объектном хранилище — и доступны только тем,
  кому доступна комната.
- Лента остаётся лёгкой: плитки грузят миниатюры, а не оригиналы.

**Non-Goals:**

- Не делается антивирусная проверка загруженного.
- Не делается редактирование состава вложений после отправки: правится только
  текст.
- Не делается переиспользование одного файла в нескольких сообщениях,
  пересылка и альбом на всю комнату.
- Не делается загрузка напрямую в хранилище по подписанной ссылке (см.
  решение 3).
- Не делается транскодирование видео и предпросмотр документов: видео
  показывается плиткой с кадром, документ — строкой.

## Decisions

### 1. Владелец файлов — сообщение, библиотека — medialibrary

`Message` реализует `HasMedia` из `spatie/laravel-medialibrary`, коллекция
одна — `attachments`. Библиотека берёт на себя запись в хранилище, миниатюры,
целостность имён и удаление файлов вместе с моделью.

Альтернатива — своя таблица `message_attachments` и ручная работа с диском —
отклонена: пришлось бы своими руками писать то, что библиотека уже делает,
включая генерацию конверсий в очереди и удаление осиротевших файлов. Выбор
библиотеки задан заданием и совпадает со списком навыков проекта
(`.ai/skills/medialibrary-development`).

Зависимость добавляется в `packages/backend/chat/composer.json`: файлы
принадлежат сообщению, значит и связь с библиотекой живёт в пакете чата, а не
в приложении. Миграция таблицы `media` приезжает от библиотеки и грузится её
провайдером — пакет её не копирует.

### 2. Вложения занимают свой префикс на общем диске

Коллекция `attachments` настраивается на префикс `uploads/` — тот, что основа
отвела вложениям. Отдельного диска не заводится: диск, его закрытость и бакет
уже заданы один раз в `add-object-storage-foundation`, и дублировать эту
настройку в пакете значит завести второе место, где её потом менять.

### 3. Файл загружается отдельным запросом, сообщение отправляется ссылками

Появляется загрузка вложения отдельным адресом в границах комнаты: клиент
отправляет файл, получает его идентификатор, и уже потом отправляет
сообщение со списком идентификаторов.

Почему не одним `multipart` вместе с сообщением: тогда прогресс по каждому
файлу отдельно не показать, повтор одного неудачного файла невозможен без
повторной отправки всех, а идемпотентность отправки (`Idempotency-Key`)
начинает означать «повторить и заливку тоже». Раздельный шаг делает
поведение из спецификации — «ошибка у одного файла, остальные не теряются» —
естественным, а не выстраданным.

Почему не подписанная ссылка прямо в хранилище: тогда проверка типа и размера
уезжает на сторону клиента и хранилища, а требование §11 — проверять MIME,
расширение, размер и право доступа на сервере — выполнить нечем. Плата —
файл идёт через приложение; для 25 МБ это приемлемо.

Загруженное, но не отправленное вложение — «висящее»: оно принадлежит автору
и комнате, но не сообщению. Такие записи удаляются по расписанию через сутки.
Иначе брошенные черновики копили бы файлы вечно.

### 4. Право на файл считается по сообщению, а не по ссылке

Выдача файла идёт через приложение: адрес вида «вложение такого-то
сообщения», политика — та же, что у чтения сообщения. Отсюда бесплатно
следуют три сценария спецификации: посторонний не получает файл, исключённый
теряет доступ вместе с членством, а удалённое сообщение перестаёт отдавать
вложения.

Альтернатива — временная подписанная ссылка от хранилища — отклонена: срок
жизни ссылки живёт своей жизнью и переживает и исключение из комнаты, и
удаление сообщения.

Ответ отдаётся как вложение (`Content-Disposition: attachment`) с типом из
белого списка: так браузер не выполнит содержимое и не отрисует чужой HTML
как страницу.

### 5. Миниатюры собираются в очереди, лента их ждёт

Миниатюра объявляется очередной конверсией в webp — в очереди для конверсий,
которую завела основа: обработка пачки фотографий не должна задерживать живую
переписку. Пока конверсия не готова, вложение отдаёт адрес миниатюры как
отсутствующий, и клиент показывает состояние ожидания — сценарий из
спецификации.

Исходный файл при этом сохраняется **как прислан**: фотографию из семейной
переписки скачивают обратно, и пережать её в webp значит необратимо испортить
отправленное. Это вторая половина правила, заданного основой, — в отличие от
аватарок, где исходник не нужен вовсе.

Размер миниатюры один и с запасом под плотный экран: два размера ради сетки
2×2 не окупаются, а третий понадобился бы только под галерею — там и так
открывается оригинал.

### 6. Тип проверяется по содержимому, а не по имени

Проверяются оба: расширение — по списку разрешённых, фактический тип — по
содержимому файла. Совпасть должны оба, иначе файл отклоняется. Список
исполняемых расширений закрывается явно, поверх белого списка типов.

Так выполняется сценарий «программа под видом документа»: одного заявленного
клиентом `Content-Type` для решения недостаточно — он приходит от клиента и
верить ему нельзя.

### 7. Сообщение считается полным по тексту ИЛИ вложениям

Правило «есть текст или есть вложение» проверяется на входе, а не только в
базе: `body` перестаёт быть безусловно обязательным. Столбец остаётся
`not null` — пустое сообщение с вложением хранит пустую строку, миграция
столбца не нужна, а форма «ни текста, ни файлов» отсекается проверкой
запроса.

### 8. Событие несёт то же, что и API

`message.created.v1` дополняется списком вложений теми же полями, что и
ответ API. Схема в `packages/contracts` расширяется, версия остаётся первой:
поле добавляется, существующие не меняются и не исчезают, а `payload`
по-прежнему содержит только то, что подписчик и так вправе получить.

Плитки должны появляться у собеседника сразу из события — иначе каждое
сообщение с фотографией заставляло бы перезапрашивать историю.

## Risks / Trade-offs

- [Файл идёт через приложение, занимая worker на время заливки] → предел 25 МБ
  и ограничение частоты; при росте требований путь к подписанной загрузке
  остаётся открытым, но тогда проверки придётся переносить на сторону
  хранилища осознанно.
- [Пачка фотографий занимает очередь конверсий] → отдельная очередь, живая
  переписка и уведомления её не ждут.
- [Висящие вложения копят место] → уборка по расписанию через сутки и предел
  на число файлов в одной отправке.
- [Белый список типов однажды не пропустит нужный формат] → список в
  конфигурации, администратор правит его без пересборки.

## Migration Plan

Схема базы не меняется: таблица медиа приходит из основы. Контракт API
расширяется добавлением поля, несовместимых изменений нет.

Предпосылка — выложенный `add-object-storage-foundation`: без него складывать
файлы некуда. Откат — возврат образа;
загруженные к тому моменту файлы останутся в хранилище и после отката будут
недоступны из интерфейса, поэтому откат уместен до того, как вложениями
начали пользоваться.
