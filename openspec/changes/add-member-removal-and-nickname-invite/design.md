## Context

Мотивация — в `proposal.md`. Ниже то, что определяет подход; проверено по коду.

- Состав комнаты меняют четыре маршрута: список, приглашение по `user_id`,
  самостоятельное вступление и выход. Удаления другого участника нет вовсе.
- `MembershipPolicy` знает `viewMembers`, `invite`, `join`, `leave` и
  `changeRole`; правила «убрать участника» в ней нет.
- Поиска людей в продукте нет ни в одном пакете: `identity` отдаёт только свой
  профиль, `MentionPicker` во фронтенде ищет по уже загруженным участникам
  комнаты.
- Пакет `chat` не обращается к моделям `identity` напрямую: имя автора он
  берёт через класс пользователя из конфигурации приложения — тем же приёмом
  доступен и поиск по нику.
- Изменения состава уже вещаются событием `room.member_changed.v1` с полями
  `user_id`, `action`, `role`; у `action` есть значение `removed`, которое
  сейчас никто не отправляет.

## Goals / Non-Goals

**Goals:**

- Пригласить человека можно, зная только его ник.
- Владелец распоряжается составом комнаты, админ помогает в разумных пределах.
- Исключённый узнаёт об этом сразу и не остаётся на экране с ошибками.

**Non-Goals:**

- Не делается блокировка: исключённый может вернуться по ссылке-приглашению
  или вступить снова, если комната публичная.
- Не делается передача владения комнатой.
- Не делается каталог пользователей и профили других людей.
- Не меняются правила ролей и способ их выдачи.

## Decisions

### 1. Исключение — отдельный маршрут, а не приглашение наоборот

Появляется `DELETE /rooms/{room}/members/{member}`, симметричный уже
существующему `PATCH` того же адреса. Выход человека остаётся на
`/members/me`: это разные действия с разными правами, и путать их адресом не
стоит.

### 2. Право «убрать» описывается в политике, а не в контроллере

В `MembershipPolicy` добавляется `remove(user, room, target)` с правилом:
владелец — любого, кроме себя; админ — только роль `member`. Так решение
лежит там же, где остальные правила комнаты, и проверяется тем же
package-тестом, что и вся матрица ролей.

Отдельный частный случай — владелец и его собственная запись: запрет здесь, а
не в обработчике, иначе комната может остаться без владельца.

### 3. Событие уже есть — используем его

Исключение рассылается существующим `room.member_changed.v1` с
`action: "removed"`. Значение в контракте описано, но не отправлялось ни разу.
Заводить новое событие ради того же смысла незачем.

Клиент, получив `removed` про себя, поступает как при удалении комнаты:
чистит кэш комнаты и уводит к списку. Эта ветка уже написана для
`room.deleted.v1` — переиспользуется.

Важная оговорка: событие уходит в канал комнаты, а подписка на приватный канал
проверяется при подписке. Исключённый ещё подписан, поэтому своё исключение
получит; отписывается он сам, уходя с экрана.

### 4. Поиск людей привязан к комнате, а не к установке

`GET /rooms/{room}/member-candidates?query=` живёт в `chat` и закрыт правом
`invite`. Это даёт две вещи сразу: список пользователей не становится
открытым (спрашивать может лишь тот, кто и так вправе позвать), и ответ может
честно помечать тех, кто уже в комнате.

Альтернатива — общий `GET /users?search=` в `identity` — превращает список
всех людей установки в открытый справочник и требует собственного правила
доступа, которого у продукта пока нет.

Ответ содержит только `id`, ник и отображаемое имя. Почты, дат и признаков
активности там нет: для приглашения они не нужны.

### 5. Поиск — по началу ника, коротко и с потолком

Запрос очищается от ведущего `@`, требует не меньше двух символов, ищет
совпадение с начала ника без учёта регистра и отдаёт не больше десяти человек.
Начало ника, а не любое вхождение: так поиск остаётся предсказуемым и не
превращается в перебор всех пользователей по подстроке.

Ограничение по частоте берётся то же, что у приглашений, — поиск не должен
стать способом выгрузить справочник ников.

### 6. Приглашение остаётся по идентификатору

Маршрут `POST /rooms/{room}/members` не меняется: он принимает `user_id`,
который интерфейс получает из результатов поиска. Менять контракт ради того,
что клиент и так знает, незачем — иначе сервер начнёт разбирать ники в двух
местах.

### 7. В интерфейсе исключение живёт рядом с ролью

Строка участника уже показывает действие «Сделать админом» тем, кто вправе.
Исключение встаёт туда же вторым действием и требует подтверждения — как и
удаление комнаты, только без ввода названия: цена ошибки здесь ниже, человека
можно позвать обратно.

## Risks / Trade-offs

- [Поиск раскрывает ники установки тому, кто вправе приглашать] → это и есть
  смысл приглашения; ответ ограничен ником и именем, запрос — десятью
  результатами и той же частотой, что у приглашений.
- [Исключённый вернётся по старой ссылке-приглашению] → осознанно: блокировки
  в продукте нет, а ссылку владелец может отозвать.
- [Админ исключает участников без ведома владельца] → это следует из
  запрошенного правила; действие видно в списке участников и в истории
  комнаты системной записью.
- [Одновременное исключение и запись сообщения] → сообщение, отправленное до
  исключения, остаётся; запрос после исключения отклоняется существующей
  проверкой членства.

## Migration Plan

Схема базы не меняется: участие удаляется из существующей таблицы. Контракт API
расширяется (новый маршрут удаления и новый маршрут поиска), несовместимых
изменений нет. Выкладка обычной пересборкой, откат — возврат образа.
