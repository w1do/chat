## Purpose

Предоставляет устанавливаемый Android/iOS-клиент чата с теми же серверными
возможностями, что и web-приложение, но с системным lifecycle мобильной ОС.

## ADDED Requirements

### Requirement: Мобильный клиент сохраняет функциональную паритетность web-чата

Мобильный клиент SHALL предоставлять доступ ко всем разрешённым пользователю
сценариям текущего web-чата: регистрации и входу, профилю, комнатам и личным
диалогам, сообщениям, ответам, реакциям, упоминаниям, вложениям, поиску,
AI-редактированию, ленте уведомлений и настройкам. Сервер SHALL оставаться
единственным источником истины; мобильный клиент SHALL использовать тот же
публичный HTTP и real-time контракт, а не отдельную копию бизнес-логики.

#### Scenario: Пользователь продолжает разговор с другого клиента

- **WHEN** пользователь входит в мобильное приложение после работы в PWA
- **THEN** он видит те же доступные комнаты, историю, профиль, права и
  непрочитанные события, полученные с self-hosted сервера

#### Scenario: Серверная функция выключена или запрещена

- **WHEN** функция выключена администратором либо недоступна пользователю по
  правам
- **THEN** мобильный клиент показывает то же доступное состояние или отказ,
  что и web-клиент, и не обходит серверную проверку

#### Scenario: Добавляется новая общая возможность чата

- **WHEN** общая React app-shell получает новую публичную функцию
- **THEN** web и mobile composition roots используют одну реализацию экрана,
  а платформенное различие ограничено явно переданным адаптером

### Requirement: Приложение подключается к одной self-hosted установке

Release-сборка SHALL быть привязана к одному заранее настроенному HTTPS API и
WSS endpoint этой установки. Приложение MUST отклонять недоверенный TLS и MUST
NOT содержать серверные, Firebase service-account или signing secrets.

#### Scenario: Корректная конфигурация установки

- **WHEN** оператор собирает приложение с валидными HTTPS/WSS адресами своей
  установки
- **THEN** клиент использует эти адреса для HTTP, загрузок, авторизации
  real-time каналов и WebSocket-соединения

#### Scenario: Сертификат недействителен

- **WHEN** сервер предъявляет просроченный, недоверенный или не совпадающий с
  именем сертификат
- **THEN** клиент не обходит проверку TLS и показывает понятную ошибку
  подключения без утечки credentials

#### Scenario: Пользователь пытается сменить сервер

- **WHEN** пользователь ищет выбор произвольной установки в первой версии
- **THEN** приложение не предлагает такой выбор и объясняет, для какого
  self-hosted сервера выпущена эта сборка

### Requirement: Lifecycle не превращает WebSocket в источник истины

Приложение SHALL корректно переживать background, resume, потерю сети и
пересоздание WebView. После восстановления соединения оно SHALL сверять
состояние через HTTP и только затем продолжать обработку real-time событий.

#### Scenario: Возврат из background

- **WHEN** приложение возвращается на экран после приостановки операционной
  системой
- **THEN** оно восстанавливает авторизацию, переподключает real-time и
  синхронизирует открытую комнату и счётчики по HTTP

#### Scenario: Сеть пропала во время работы

- **WHEN** HTTP и WebSocket недоступны
- **THEN** интерфейс явно показывает offline/reconnecting state и не выдаёт
  неотправленную мутацию за подтверждённую сервером

#### Scenario: Соединение восстановилось

- **WHEN** сеть снова доступна
- **THEN** клиент получает актуальные данные через HTTP, устраняет пропуски и
  дубли и возобновляет real-time подписки

### Requirement: Оболочка учитывает системную геометрию и ввод

Основные сценарии SHALL работать в portrait на поддерживаемых Android/iOS
устройствах с safe areas, экранной клавиатурой и системными жестами. Поле
ввода, текущий черновик и активное действие MUST оставаться доступными при
появлении/скрытии клавиатуры, а приложение SHALL сохранять WCAG 2.2 AA для
web-содержимого и доступные имена элементов управления.

#### Scenario: Клавиатура открыта в комнате

- **WHEN** пользователь набирает сообщение на устройстве с нижним системным
  индикатором или вырезом экрана
- **THEN** композер целиком виден, не перекрыт клавиатурой или safe area и не
  вызывает прокрутку всей оболочки

#### Scenario: ОС пересоздала WebView

- **WHEN** WebView пересоздана после memory pressure или смены lifecycle
- **THEN** приложение восстанавливает маршрут и незавершённый безопасный UI
  state либо честно сообщает о потере черновика, не публикуя его автоматически

#### Scenario: Пользователь использует assistive technology

- **WHEN** включён screen reader, увеличенный текст или внешняя клавиатура
- **THEN** основные auth, room, messaging, notification и settings сценарии
  остаются доступными и имеют понятный focus order

### Requirement: Внутренние ссылки открывают нужный экран приложения

Клиент SHALL принимать разрешённые room/invite links и переходы из системных
уведомлений как внутреннюю навигацию. Неизвестные и внешние URL SHALL NOT
получать доступ к native bridge и SHALL открываться только по безопасной
политике внешних ссылок.

#### Scenario: Холодный старт из уведомления

- **WHEN** пользователь нажимает системное уведомление при выгруженном
  приложении
- **THEN** после запуска и проверки сессии открывается указанная доступная
  комната, а при отсутствии доступа показывается безопасный not-found/forbidden
  state

#### Scenario: Ссылка-приглашение

- **WHEN** установленное приложение получает поддерживаемую invite link
- **THEN** оно открывает существующий сценарий приглашения и сохраняет токен
  до завершения входа или регистрации

#### Scenario: Внешняя ссылка в сообщении

- **WHEN** пользователь открывает внешний URL из сообщения
- **THEN** URL не загружается в привилегированном origin с native bridge и
  обрабатывается системным браузером либо подтверждённым безопасным WebView

### Requirement: PWA продолжает работать независимо

Добавление native-клиента MUST NOT изменять установку PWA, cookie-based auth,
service worker, VAPID Web Push или desktop layout существующего web-клиента.

#### Scenario: Установка без mobile credentials

- **WHEN** оператор обновляет обычный Docker Compose стек и не настраивает
  mobile/Firebase credentials
- **THEN** PWA и все её существующие проверки продолжают работать, а native
  возможности явно считаются не настроенными
