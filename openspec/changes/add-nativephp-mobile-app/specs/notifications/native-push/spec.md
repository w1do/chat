## Purpose

Доставляет уведомления чата в системный центр Android/iOS через FCM/APNs,
сохраняя предпочтения и надёжность существующего notification-домена.

## ADDED Requirements

### Requirement: Пользователь осознанно включает системные уведомления

Мобильный клиент SHALL сначала объяснить назначение уведомлений и показать
системный запрос только после явного действия пользователя. Настройки SHALL
различать состояния not determined, granted, denied, server not configured и
registration failed и MUST NOT обещать доставку без подтверждённой сервером
регистрации устройства.

#### Scenario: Разрешение ещё не запрашивалось

- **WHEN** пользователь нажимает «Включить уведомления» после пояснения
- **THEN** приложение вызывает системный permission prompt и при согласии
  регистрирует полученный token на сервере

#### Scenario: Разрешение запрещено

- **WHEN** операционная система сообщает denied
- **THEN** приложение не повторяет системный prompt бесконечно и объясняет,
  как изменить разрешение в системных настройках

#### Scenario: Сервер не подтвердил регистрацию

- **WHEN** ОС выдала token, но API регистрации недоступен или отклонил запрос
- **THEN** переключатель не показывает «включено», а повтор регистрации
  выполняется при следующем безопасном resume/reconnect

### Requirement: Native-устройство регистрируется идемпотентно

API SHALL связывать installation identifier, platform, push token и app
version с текущим пользователем. Одна installation SHALL иметь не более одной
активной регистрации, повторная отправка SHALL обновлять её, а новый token от
FCM/APNs SHALL заменять старый без создания дубля. Token и полный device
fingerprint MUST NOT выводиться в ответах и логах.

#### Scenario: Первая регистрация

- **WHEN** авторизованное приложение впервые отправляет installation id,
  platform и push token
- **THEN** сервер создаёт активную регистрацию текущего пользователя и
  возвращает неприватный идентификатор/статус ресурса

#### Scenario: FCM заменил token

- **WHEN** та же installation сообщает новый token после update, restore или
  внутренней ротации
- **THEN** старая регистрация атомарно обновляется и уведомления больше не
  отправляются на прежний token

#### Scenario: На устройстве вошёл другой пользователь

- **WHEN** после logout на той же installation входит другой пользователь
- **THEN** token не остаётся привязанным к прежнему аккаунту и регистрируется
  только после новой подтверждённой mobile session

#### Scenario: Пользователь выключил push

- **WHEN** пользователь выключает системные уведомления в приложении или
  выходит из аккаунта
- **THEN** сервер деактивирует регистрацию этой installation и новые push на
  неё не отправляются

### Requirement: Native push использует общие правила уведомлений

Native push SHALL быть транспортом существующего канала `push` и SHALL
соблюдать категории, предпочтения, подавление инициатора и активного
получателя, группировку и приоритет очередей. При наличии PWA и native
регистраций сервер SHALL доставлять на каждый активный транспорт без изменения
database/mail каналов.

#### Scenario: Получатель читает комнату

- **WHEN** получатель активен в комнате, где создано сообщение
- **THEN** native push о нём не отправляется по тому же presence-правилу, что
  и Web Push

#### Scenario: Push категории выключен

- **WHEN** пользователь выключил push для категории
- **THEN** ни FCM/APNs, ни Web Push этой категории не отправляются, а включённые
  database/mail каналы продолжают работать

#### Scenario: У пользователя два native устройства и PWA

- **WHEN** пользователю положено уведомление и все три регистрации активны
- **THEN** одно логическое событие ставится идемпотентно и доставляется один
  раз на каждое устройство/transport без дублирования внутри регистрации

### Requirement: Системное уведомление раскрывает минимум данных

Visible push SHALL содержать только безопасный title, короткий preview,
category, collapse key/tag, badge metadata и внутренний относительный route.
Payload MUST NOT содержать credentials, полный message body, скрытые room
данные или произвольный внешний URL. Политика preview SHALL совпадать с Web
Push и документировать видимость текста на lock screen.

#### Scenario: Длинное сообщение

- **WHEN** preview длиннее настроенного безопасного предела
- **THEN** сервер обрезает его до отправки в FCM/APNs

#### Scenario: Несколько сообщений одной комнаты

- **WHEN** до открытия приложения приходит несколько уведомлений одной
  категории и комнаты
- **THEN** операционная система схлопывает их по стабильному ключу и показывает
  актуальное уведомление и корректный badge вместо очереди устаревших

#### Scenario: Нажатие на уведомление

- **WHEN** пользователь нажимает visible push в background или после cold start
- **THEN** приложение открывает только разрешённый внутренний route указанной
  комнаты после проверки mobile session и server authorization

### Requirement: Сбой native push изолирован и восстанавливаем

Доставка SHALL выполняться асинхронно после commit с ограниченными retry,
backoff, timeout, audit-safe failed handling и idempotency. Постоянно
невалидный token SHALL деактивироваться; временная ошибка SHALL повторяться.
Сбой FCM/APNs MUST NOT откатывать сообщение, ломать Web Push или блокировать
доставку на другие устройства.

#### Scenario: FCM временно недоступен

- **WHEN** transport отвечает временной ошибкой или timeout
- **THEN** job повторяется по ограниченной политике, сообщение остаётся
  отправленным, а логи содержат только безопасный reason и trace context

#### Scenario: Token окончательно недействителен

- **WHEN** transport сообщает unregistered/invalid token
- **THEN** регистрация деактивируется без повторов и пользователь сможет
  восстановить её при следующей выдаче token приложению

#### Scenario: FCM упал, Web Push доступен

- **WHEN** у пользователя есть оба транспорта, но FCM delivery падает
- **THEN** Web Push всё равно получает своё уведомление, а ошибка FCM
  обрабатывается отдельно

### Requirement: Native push не требует центрального vendor relay

Self-hosted API SHALL отправлять native push напрямую через Firebase project
оператора; APNs SHALL использоваться через настройку этого Firebase project.
При отсутствии credentials native push SHALL быть выключен с явной
диагностикой, а PWA/Web Push SHALL оставаться работоспособными.

#### Scenario: Установка настроила Firebase

- **WHEN** сервер имеет действующий service account, а mobile build содержит
  соответствующие публичные platform config files
- **THEN** тестовая команда и обычная очередь могут доставить уведомление на
  зарегистрированное физическое устройство

#### Scenario: Firebase не настроен

- **WHEN** service account или platform config отсутствуют
- **THEN** native push не предлагается как рабочий, диагностика называет
  недостающую часть без раскрытия секрета, а остальные каналы не деградируют
