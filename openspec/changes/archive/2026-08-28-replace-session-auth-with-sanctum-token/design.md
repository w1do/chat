## Context

Мотивация — в `proposal.md` («Why»), контракт — в
`specs/identity/token-authentication/spec.md`. Здесь только то, что нужно, чтобы
объяснить решения.

Сегодня в репозитории сосуществуют два механизма входа, и оба завязаны на
браузер:

- `apps/chat-api/bootstrap/app.php` включает `$middleware->statefulApi()`, то
  есть запросы SPA проходят session + CSRF стек Sanctum (ADR-005);
- `packages/backend/identity` дополнительно выдаёт cookie
  `__Host-chat_browser_token` (`BrowserTokenLifecycle`) и разбирает её
  middleware `UseBrowserTokenCookie`, подставляя пользователя по токену.

Cookie с префиксом `__Host-` браузер обязан отбросить, если у неё нет атрибута
`Secure`. В `docker-compose.yml` `APP_ENV: production`, поэтому
`identity.browser_token.secure` истинно и `Secure` ставится, а сам стек при
этом отдаётся по `http` (`APP_URL: http://localhost`,
`SESSION_SECURE_COOKIE: false`). Cookie до сервера не возвращается, авторизация
остаётся сессионной, и через `SESSION_LIFETIME` (120 минут по умолчанию) человек
получает `401`. Ровно это он и наблюдает.

Ограничения, в которых принимается решение:

- клиент и API живут за одним reverse proxy, но это перестаёт быть требованием;
- `personal_access_tokens` уже есть, `sanctum.expiration` уже `null`;
- Octane переиспользует worker между запросами — identity нельзя кэшировать;
- аватарки, фото комнат и вложения отдаются защищёнными эндпоинтами и рисуются
  как `<img src>`; service worker кеширует их по адресу;
- владелец продукта явным решением выбрал токен в `localStorage`, приняв
  связанный с этим риск XSS.

## Goals / Non-Goals

**Goals:**

- Один способ авторизации: bearer-токен без срока жизни.
- Ни одна ветка запроса к `/api/v1/**` и `/broadcasting/auth` не читает сессию
  и не проверяет CSRF.
- Удалить, а не отключить, обвязку browser-token cookie и экран «Сессия
  истекла»: мёртвый код продолжал бы объяснять поведение, которого нет.
- Картинки и вложения продолжают показываться и кешироваться на устройстве.
- Отзыв остаётся возможным: выход, смена и сброс пароля.

**Non-Goals:**

- Refresh-токены, ротация, срок жизни, «доверенные устройства», список активных
  сессий в настройках.
- Ограничение прав токена (abilities): единственный клиент — сам чат, токен
  получает `*`.
- Шифрование хранилища браузера и защита от XSS хранением вне JS: решение
  сознательно отвергнуто владельцем продукта.
- Изменение схемы данных: миграции этот change не добавляет.

## Decisions

### 1. Токен выдаётся при входе и не имеет срока

`createToken('client', ['*'])` без третьего аргумента — Sanctum пишет
`expires_at = null`, `sanctum.expiration` уже `null`, поэтому истечения нет
нигде. Plaintext возвращается один раз, в теле `/auth/login` и
`/auth/register`; в базе лежит хэш.

Альтернатива — короткий токен плюс refresh — отвергнута: она возвращает ровно
ту проблему, ради которой затеян change (человека просят войти заново), и
требует хранить второй секрет.

Ответ входа становится `{"data": {…user…}, "token": "..."}`. Прежний envelope
пользователя сохраняется, добавляется одно поле — это расширение контракта, а не
его слом; ломает контракт удаление `remember` (см. решение 8).

### 2. Вход не создаёт сессию

`LoginHandler` перестаёт использовать `StatefulGuard::attempt()` — этот вызов
существует только ради сессии. Проверка учётных данных идёт через
`UserProvider::retrieveByCredentials()` + `validateCredentials()`: то же
сравнение хэша и та же защита от подбора по времени, но без session store.
`AuthController` перестаёт вызывать `session()->regenerate()` и
`session()->invalidate()`.

`config('identity.guard')` («web») больше не нужен и уходит из конфигурации
пакета: пакет не должен знать про guard, которого не использует.

### 3. Все защищённые маршруты — под общим `auth:sanctum`

`UseBrowserTokenCookie` удаляется, маршруты identity переходят на
`auth:sanctum`, как chat/ai/notifications/administration. Один способ
авторизации на весь API — меньше мест, где поведение может разойтись.

В `config/sanctum.php` `stateful` становится пустым, `guard` — пустым массивом.
Пустой `guard` важен: иначе Sanctum при отсутствии bearer-токена пробует
session-guard `web`, и молчаливый fallback снова появляется в системе.

`$middleware->statefulApi()` уходит из `bootstrap/app.php`. Группа `web`
остаётся зарегистрированной Laravel по умолчанию и используется только
Horizon-дашбордом (`config/horizon.php`, gate `viewHorizon`) — это инструмент
оператора, не часть контракта чата, и он этим change не затрагивается.

### 4. Real-time авторизуется тем же заголовком

`Broadcast::routes(['middleware' => ['auth:sanctum', TouchLastSeen::class]])` —
без `web`. Echo получает `auth.headers.Authorization` геттером, читающим
текущий токен (так же, как сейчас читается `XSRF-TOKEN`), чтобы после
повторного входа сокет не остался со старым значением.

### 5. Картинки: авторизованный fetch и `blob:`-URL

Браузер не приложит `Authorization` к `<img src>`, поэтому вводится
`<AuthorizedImage>` (и хук `useAuthorizedImage`) в `@vendor/ui`: он делает
`fetch(url, { headers: { Authorization } })`, создаёт `URL.createObjectURL` и
отзывает его при размонтировании. Потребители — `Avatar`, `RoomGlyph`,
`AttachmentTiles`, `AttachmentGallery`, `AvatarPicker`, `MentionPicker`,
`MemberRow`.

Почему не подписанные ссылки: подпись подменяет проверку прав знанием адреса
(вложение из чужой комнаты открылось бы по пересланной ссылке), а меняющийся
`expires` в query ломает ключ кеша service worker'а — каждая перезагрузка
скачивала бы картинки заново.

Почему не подстановка заголовка в service worker: он живёт только в secure
context. Установка по `http` — ровно тот случай, который сломал cookie; там
картинки просто перестали бы грузиться.

Кеш при этом сохраняется: `fetch` из страницы проходит через service worker,
адрес не меняется, и запись `chat-images-v1` остаётся валидной. Чтобы заголовок
`Vary` не разрушил совпадение, `cache.match` в `public/sw.js` получает
`{ ignoreVary: true }`. Один общий in-flight-реестр по адресу не даёт двум
компонентам скачать одну и ту же миниатюру дважды.

`image-prewarm.ts` переходит с `credentials: 'include'` на тот же заголовок.

### 6. Хранение токена и его владелец

`apps/chat-web/src/app/token.ts` — единственный владелец значения:
`localStorage['chat.auth-token']`, чтение/запись/очистка и подписка. Все чтения
`localStorage` обёрнуты в `try/catch`: приватный режим не должен ронять
приложение (spec, «Хранилище недоступно»).

`ApiClient` получает необязательный `authToken?: () => string | null` — тем же
способом, каким приложение уже передаёт `sessionSuspended`. Пакет не лезет в
`localStorage` сам: `@vendor/api-client` должен оставаться переиспользуемым
(§4.2), а мобильная оболочка (`add-nativephp-mobile-app`) хранит токен иначе.

Событие `storage` синхронизирует вкладки: выход в одной гасит остальные без
опроса сервера.

### 7. 401 после входа

Остаётся один механизм из `fix-auth-401-session-expiry-loop` — подавление
повторов: первый `401` переводит клиент в состояние «вход недействителен», и
защищённые запросы дальше не уходят в сеть. Всё остальное удаляется: экран
`SessionExpiredScreen`, «тихое восстановление» через CSRF-handshake,
runtime-флаг `silentRecovery`, `ApiClient.refreshCsrfCookie()`. Переход
означает: стереть токен, отключить сокет, очистить кеш изображений, уйти на
`/login`.

До входа (токена нет) `401` по-прежнему не является инцидентом: `/login` и
`/invite/{token}` работают как раньше.

### 8. `remember` удаляется

Поле уходит из `LoginRequest`, `LoginCommand`, схемы формы, `LoginForm` и
OpenAPI. Токен и так бессрочен, и оставленный флажок обещал бы человеку выбор,
которого нет. Поле необязательное, поэтому клиент, который его не шлёт, не
ломается; в upgrade notes — явная строка о его исчезновении.

`ChangePasswordHandler` и `ResetPasswordHandler` сохраняют обновление
`remember_token` (это защита `web`-guard'а, не наша схема), но главным
действием становится отзыв токенов.

### 9. Отзыв

- выход: `$user->currentAccessToken()->delete()` — только это устройство;
- сброс пароля: `$user->tokens()->delete()` — все;
- смена пароля в настройках: удаляются все, кроме `currentAccessToken()`, иначе
  человек разлогинивал бы сам себя посреди настроек.

### 10. Push-подписка из service worker

`pushsubscriptionchange` больше не отправляет подписку сам: читать
`localStorage` из worker'а нельзя, а дублировать туда токен значило бы завести
второе хранилище учётных данных. Worker только перевыпускает подписку, а
приложение при следующем запуске сверяет её с сервером и отправляет
авторизованным запросом (`POST /push-subscriptions` идемпотентен). Это меняет
момент доставки, но не результат: сегодня в браузерах без Cookie Store API
поведение ровно такое же.

## Risks / Trade-offs

- **XSS крадёт бессрочный токен** → Явное решение владельца продукта. Смягчения
  в пределах change'а: токен лежит по одному известному ключу и стирается при
  `401` и выходе; отзыв всех токенов при сбросе пароля даёт способ прекратить
  доступ; пользовательский текст по-прежнему не рендерится как HTML. В ADR-012
  этот риск и его принятие фиксируются письменно, в threat model — тоже.
- **Токен не истекает никогда** → Украденный или забытый на чужом устройстве
  токен действует, пока его не отозвали. Отзыв доступен через выход и сброс
  пароля; списка активных устройств в MVP нет — это отдельная задача.
- **Разовый разлогин при обновлении** → Cookie-сессии перестают признаваться;
  все входят заново один раз. Пишется в upgrade notes и CHANGELOG как ожидаемое
  поведение обновления.
- **Регресс кеша изображений** → Если `blob:`-подход или `ignoreVary` окажутся
  неверными, картинки будут скачиваться заново на каждой перезагрузке. Проверка:
  E2E-сценарий, который открывает ленту дважды и убеждается, что второй показ
  идёт из кеша.
- **Много точек правки во фронтенде** → Семь компонентов переходят на
  `<AuthorizedImage>`; пропущенный превратится в «битую» картинку. Проверка:
  grep по `<img src=` в `packages/frontend` и `apps/chat-web` в задаче 4 плюс
  E2E `profile-images` и `attachments`.
- **`GET /me` остаётся единственной проверкой токена при старте** → Если
  эндпоинт недоступен, приложение не отличит «сервер лежит» от «токен отозван».
  Токен стирается только по `401`, но не по сетевой ошибке — это уже поведение
  `ApiClient`, и оно сохраняется.

## Migration Plan

1. Backend и frontend меняются одним релизом: старый клиент не умеет
   `Authorization`, новый — cookie, поэтому промежуточного совместимого
   состояния нет и не планируется.
2. Миграций базы нет. Ранее выданные browser-token'ы остаются строками в
   `personal_access_tokens` и просто перестают приходить в запросах; их
   `expires_at` доводит их до неактуальности сам. Отдельная уборка не нужна.
3. Из окружения удаляются `SANCTUM_STATEFUL_DOMAINS`, `SESSION_SECURE_COOKIE` и
   `AUTH_BROWSER_TOKEN_*` (`.env.example`, `docker-compose.yml`). Оставленные в
   чужом `.env` значения безвредны: их больше никто не читает.
4. После деплоя — `octane:reload`, чтобы worker'ы не держали старую
   конфигурацию middleware.
5. Откат — возврат предыдущего образа: схема данных не менялась, поэтому откат
   безопасен; людям придётся войти ещё раз, теперь уже в cookie-схему.
6. Проверка на стенде: вход, перезагрузка страницы, перезапуск браузера,
   перезапуск контейнера `api`, показ аватарок и вложений, приход сообщения по
   WebSocket, выход, вход со второго устройства и выход только на одном.
