## Context

Мотивация — в `proposal.md`. Ниже состояние, которое определяет подход
(проверено по коду).

- Уведомления уже разнесены по категориям и каналам: `Channel` знает
  `database` и `mail`, `NotifyRoomEventHandler` решает, кому уведомление
  положено (не инициатору, не тому, кто в комнате), группирует шумные события
  и ставит `DeliverNotificationJob` в очередь категории. Push логично
  добавляется третьим каналом, а не отдельной подсистемой.
- Уведомления браузера сейчас ставит сам SPA (`raiseSystemNotification`) при
  открытой вкладке — это не push и с закрытым приложением не работает.
- Настройки интерфейса живут локально (`apps/chat-web/src/app/settings.ts`),
  а предпочтения каналов — на сервере (`/notification-preferences`).
- Оболочка приложения жёстко мобильная: `max-w-md`, слой переписки
  выезжает поверх списка (`translateX`).
- Окружение разработки без внешней сети; composer-пакеты ставятся через
  контейнер с сетью. Библиотеки Web Push в локальном кеше нет.

## Goals / Non-Goals

**Goals:**

- Доставлять уведомление на устройство при закрытом приложении.
- Дать поставить приложение на телефон и компьютер.
- Показать на широком экране две колонки.
- Управлять push одним понятным тумблером.

**Non-Goals:**

- Не вводится нативное приложение и магазины приложений.
- Не делается полноценная оффлайн-работа с очередью исходящих сообщений:
  оффлайн — это честный экран, а не второй режим работы.
- Не меняются правила, кому положено уведомление: push подчиняется
  существующим.
- Не вводится Firebase или другой внешний control plane: Web Push работает
  через push-сервис самого браузера, ключи VAPID — свои.

## Decisions

### 1. Push — третий канал существующего пакета, а не новая подсистема

`Channel::Push` добавляется в enum, подписки живут в таблице
`push_subscriptions` пакета `notifications`, отправка выполняется тем же
`DeliverNotificationJob` (ветка по каналу). Так push автоматически получает
правило «не уведомлять того, кто в комнате», группировку, идемпотентность,
retry/backoff и очередь категории — то, что уже написано и покрыто тестами.

Альтернатива — отдельный пакет `push`: пришлось бы дублировать правила
доставки и следить, чтобы они не разошлись.

### 2. Web Push с VAPID, без стороннего сервиса

Отправка идёт напрямую в push-сервис браузера (Google, Mozilla, Apple) с
подписью VAPID. Никаких аккаунтов Firebase: self-hosted установка не должна
зависеть от внешнего control plane (CLAUDE.md §14).

Шифрование полезной нагрузки (`aes128gcm`) и подпись `ES256` руками писать не
будем — берём `minishlink/web-push`. В offline-окружении пакет ставится через
networked-контейнер composer, как это уже делалось для остальных
зависимостей.

Ключи VAPID генерируются командой `php artisan chat:push-keys` и кладутся в
`.env` (`VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`). Публичный
ключ отдаётся SPA через уже существующий runtime-config (`/config.json`),
поэтому пересборка образа при смене ключа не нужна.

Если ключи не заданы — push просто выключен: канал не предлагается в
настройках, подписка не запрашивается, остальные каналы работают.

### 3. Подписка — ресурс пользователя, endpoint как естественный ключ

`push_subscriptions`: `id`, `user_id`, `endpoint` (уникален), `p256dh`,
`auth`, `user_agent`, `created_at`, `last_used_at`. Повторная подписка того же
устройства — `updateOrCreate` по endpoint. Ответ push-сервиса `404`/`410`
удаляет подписку: браузер её уже аннулировал.

### 4. Service worker пишем сам, без сборочного плагина

Нужны две вещи: обработка `push`/`notificationclick` и оффлайн-заглушка.
Плагин вроде `vite-plugin-pwa` тянет Workbox и генерирует стратегии кеша,
которых для чата не требуется: данные и так живут в TanStack Query и
досинхронизируются после reconnect.

Кешируем только оболочку (`index.html`, собранные ассеты) стратегией
network-first для навигации; API и WebSocket не кешируются никогда — иначе
пользователь увидит вчерашнюю переписку как свежую.

Обновление: новый service worker сообщает приложению, что готов; SPA
показывает ненавязчивое «доступно обновление» и применяет его по
подтверждению либо при следующем запуске.

### 5. Тумблер push включает и выключает подписку

Тумблер в настройках — единственная точка управления: включение запрашивает
разрешение браузера и создаёт подписку, выключение удаляет её на сервере и
отписывает браузер. Состояние выводится из фактов, а не хранится отдельно:
есть подписка и разрешение — включено.

Особые случаи, которые интерфейс объясняет словами: разрешение запрещено в
браузере; push не поддерживается; на iPhone push доступен только для
установленного приложения.

Тумблер выключает только системные уведомления. Лента и письма остаются: они
подчиняются предпочтениям категорий (решение пользователя, вопрос 3).

### 6. Раскладка выбирается по ширине окна

`useMediaQuery('(min-width: 1024px)')` в `@vendor/ui`. User-agent не
используется: он врёт на планшетах и в режиме рабочего стола браузера, а
ширина отражает то, что человек реально видит.

На широком экране `ChatPage` рендерит две колонки: слева `RoomsScreen`,
справа либо `ChatScreen`, либо приглашение выбрать комнату. Компоненты
переиспользуются как есть — меняется только контейнер, поэтому мобильный
путь не раздваивается.

Маршрут остаётся источником истины (`/rooms/:roomId`), поэтому ссылка на
комнату работает одинаково в обеих раскладках.

## Risks / Trade-offs

- [Push на iOS работает только у установленного PWA] → тумблер объясняет это
  словами и предлагает установку; на неподдерживаемых версиях канал не
  предлагается.
- [Библиотека Web Push недоступна в offline-окружении] → ставится через
  networked-контейнер composer; версия фиксируется в `composer.lock`, сборка
  образа её не докачивает.
- [Push-сервис отвечает медленно или падает] → отправка в очереди с
  ограниченными retry; провал не влияет на сообщение и на остальные каналы.
- [Push раскрывает текст на экране блокировки] → в уведомление идёт короткий
  фрагмент; в спецификации это зафиксировано, а в документации предупреждаем.
- [Service worker закеширует старую версию] → навигация network-first,
  ассеты с хешами в именах, явное сообщение об обновлении.
- [Две колонки — второй путь в интерфейсе, который может разойтись с
  мобильным] → переиспользуются те же компоненты, различие только в
  контейнере; тесты покрывают обе раскладки.
- [Ключи VAPID потеряны при переносе установки] → документируем в ротации
  секретов: смена ключей аннулирует подписки, пользователям нужно включить
  push заново.

## Migration Plan

Миграция данных не требуется: добавляется таблица подписок и значение канала.
Существующие предпочтения остаются валидными — для новых записей канал push
получает значение по умолчанию своей категории.

Выкладка: обычная (`docker compose up -d --build`), затем `php artisan
migrate --force`. Установка без ключей VAPID продолжает работать без push.

Откат: возврат образа предыдущей версии; таблица подписок остаётся и не
мешает. Service worker при откате получает пустую регистрацию — предусмотреть
`unregister` в откатной инструкции.
