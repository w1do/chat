## Context

Мотивация — `proposal.md`, требования — `specs/`.

Что есть сегодня:

- Миниатюра вложения — конверсия `preview` медиатеки, зарегистрированная
  трейтом `PreparesAttachmentPreviews` с `->queued()`; очередь `media`
  (`media-library.queue_name`).
- `AttachmentData::fromMedia()` отдаёт `thumb_url` только при
  `hasGeneratedConversion('preview')`, иначе `null`. Маршрут
  `GET /attachments/{uuid}/thumb` при неготовой конверсии отвечает 404.
- Плитка `AttachmentTiles.ImageTile` при `thumb_url === null` рисует серую
  заглушку с иконкой. Перезапроса нет ни по событию, ни по таймеру, поэтому
  заглушка живёт до перезагрузки приложения.
- Изображения уже отдаются с `Cache-Control: private, max-age=31536000,
  immutable` (вложения, аватарки, фото комнат) — то есть HTTP-кеш работает, но
  вытесняется браузером первым и офлайн ничего не гарантирует.
- Service worker (`apps/chat-web/public/sw.js`) намеренно не кеширует данные:
  перехватывает только навигацию ради экрана «нет связи».
- Есть точечный `GET /messages/{message}` — им можно перечитать одно сообщение.
- В приложении уже есть состояние сессии (`app/session.ts`, `AuthProvider`):
  выход и «сессия истекла» проходят через одно место — туда же удобно повесить
  очистку кеша изображений.

## Goals / Non-Goals

**Goals:**

- Убрать класс «серой плитки» в типовом случае целиком, а не прикрывать его
  индикатором ожидания.
- Оставить отложенный путь для тяжёлых файлов и сделать его самозаживающим,
  без бесконечного опроса и без нового версионированного события.
- Дать изображениям управляемое хранилище на устройстве с понятными пределами
  и честной очисткой при смене человека.

**Non-Goals:**

- Кеширование данных переписки (сообщений, комнат, уведомлений). Инвариант
  service worker'а сохраняется: только оболочка и изображения.
- Кеширование полноразмерных изображений и не-изображений. Кеш — для
  миниатюр и картинок профиля/комнаты.
- Офлайн-отправка сообщений и очередь исходящих.
- Смена формата, размеров и маршрутов изображений; правки OpenAPI.

## Decisions

### 1. Миниатюра готовится синхронно, если файл меньше порога

`registerMediaConversions(?Media $media)` получает конкретный media-объект,
поэтому решение принимается на месте: файл до
`chat.attachments.preview_sync_max_kb` (по умолчанию 4096 КБ) готовится
`->nonQueued()`, больше — как сейчас, `->queued()`. Ответ на загрузку тогда
содержит `thumb_url`, и в ленту (и в `message.created.v1`) миниатюра попадает
уже готовой.

Альтернативы:

- *Всегда синхронно*: пачка из десяти 20-мегабайтных снимков держит HTTP-воркер
  Octane десятки секунд — отправка встанет ради миниатюры.
- *Отдавать оригинал, пока миниатюра не готова* (так сделано у аватарок): у
  аватарки «оригинал» — уже подготовленный webp 512 px, у вложения это может
  быть 25 МБ с телефона. Лента на мобильном канале этого не переживёт.
- *Ресайз на лету при запросе `/thumb`*: тратит CPU на каждый промах кеша и
  плохо сочетается с `immutable`.

Порог — по размеру файла, а не по пикселям: размер известен до чтения файла и
не требует декодирования картинки ради решения.

### 2. Отложенный случай догоняется точечным перезапросом, а не новым событием

Плитка, увидевшая `thumb_url === null`, планирует до трёх перезапросов
`GET /messages/{message}` с возрастающими паузами (≈2 с, 5 с, 12 с) и
подменяет данные вложения, как только миниатюра появилась. После последней
попытки плитка перестаёт спрашивать и предлагает открыть оригинал.

Альтернатива — новое событие `attachment.preview_ready.v1`: точнее и дешевле по
трафику, но это версионированный контракт, JSON Schema, contract-тест,
broadcast из джоба конверсии и правки в `eventMap`/`EchoAdapter`. По правилу
выбора сложности (CLAUDE.md §20) при пороге, покрывающем типовой случай,
догоняющий запрос проще и достаточен. Если после выката окажется, что
отложенный путь массовый, событие можно добавить отдельным изменением.

Три попытки, а не «пока не появится»: конверсия может не появиться никогда
(битый файл, упавший воркер), и вечный опрос превратился бы в фоновый шум.
Паузы возрастают, чтобы десять плиток одного сообщения не били по серверу
синхронно; запрос идёт один на сообщение, а не на каждую плитку.

### 3. Кеш изображений — Cache Storage в service worker, cache-first

Отдельный кеш `chat-images-v1`, стратегия «сначала кеш, при промахе сеть с
последующей записью». Перехватываются только GET-запросы изображений: маршруты
миниатюр вложений и изображений профиля/комнаты. Всё остальное — как раньше.

Почему не полагаться на HTTP-кеш, который уже настроен: он не даёт ни
гарантии офлайн, ни контроля над вытеснением — браузер выбрасывает его первым и
именно поэтому картинки грузятся заново при каждом открытии.

Почему не IndexedDB: Cache Storage работает с `Request`/`Response` напрямую,
переживает перезапуск и уже используется оболочкой.

**LRU без отдельного индекса.** Cache Storage не хранит метаданных, но
`cache.keys()` возвращает записи в порядке вставки. Поэтому попадание в кеш
переписывает запись (удалить и положить заново = перенести в конец), а
подрезка удаляет записи с начала, пока их не станет меньше предела. Получается
LRU без второй базы и без счётчиков.

Пределы: не больше `IMAGE_CACHE_MAX_ENTRIES` записей (по умолчанию 400) и не
кешируются ответы больше `IMAGE_CACHE_MAX_ENTRY_KB` (по умолчанию 2048 КБ).
Миниатюра webp 640 px весит около 50–150 КБ, аватарка — единицы, поэтому
верхняя граница объёма получается порядка десятков мегабайт по построению, без
подсчёта байтов на лету.

Ответы с ошибкой не кешируются вовсе — в том числе 404 неготовой миниатюры,
иначе она осталась бы «навсегда неготовой» на этом устройстве.

### 4. Прогрев делает приложение, а не service worker

Прогрев — обычный `fetch` с `credentials: 'include'` из приложения: он проходит
через service worker и попадает в тот же кеш, поэтому отдельный канал общения с
worker'ом не нужен, а без установленного worker'а прогрев просто греет
HTTP-кеш.

Очередь с параллельностью 3, старт по `requestIdleCallback` (fallback —
`setTimeout`), адреса берутся из уже загруженных данных: миниатюры последних
сообщений открытой истории и изображения комнат из списка переписок. Повторно
уже запрошенный адрес не запрашивается — множество отданных адресов живёт в
памяти вкладки.

Альтернатива — прогрев по таймеру всего подряд: тратит трафик человека на
переписки, которые он не откроет, и соперничает с живой лентой за канал.

### 5. Очистка кеша привязана к состоянию сессии

Кеш чистится сообщением service worker'у (`clear-images`) в трёх точках:
выход из аккаунта, переход в «сессия истекла» и обнаружение другого
пользователя в `/me` (идентификатор последнего входа хранится локально). Третья
точка — предохранитель: вход другим человеком без явного выхода не должен
оставлять ему чужие фотографии.

Без установленного service worker'а очистка выполняется прямым удалением кеша
из приложения — `caches.delete()` доступен и в окне.

## Risks / Trade-offs

- Синхронная конверсия удлиняет загрузку файла на время подготовки миниатюры
  → порог по размеру и измерение на реальном файле при приёмке; при
  превышении порога поведение остаётся прежним.
- Порог подобран неверно и отложенный путь становится массовым → порог задаётся
  установкой (`ATTACHMENT_PREVIEW_SYNC_MAX_KB`), меняется без пересборки
  образа; догоняющий запрос страхует любой случай.
- Три перезапроса не покрыли долгую конверсию (перегруженная очередь) →
  плитка остаётся честной и открывает оригинал; следующая загрузка истории
  покажет готовую миниатюру.
- Закешированные изображения остаются на устройстве после исключения человека
  из комнаты → это уже свойство HTTP-кеша с `immutable`; смягчение — очистка
  при выходе и смене аккаунта, ограниченный предел записей и отказ кешировать
  оригиналы.
- Прогрев тратит трафик → греются только ближайшие изображения уже открытых
  списков, параллельность ограничена, повторов нет.
- Ошибка в перехвате `fetch` в service worker ломает загрузку изображений
  целиком → перехват сужен до GET изображений, любой сбой кеша падает обратно в
  сеть, версия кеша поднимается при выкате.

## Migration Plan

- Новая версия service worker поднимает имя кеша и удаляет прежние; применение —
  по команде приложения, как и сегодня (кнопка обновления), поэтому посреди
  работы ничего не подменяется.
- Откат: вернуть `->queued()` без условия и снять перехват изображений в service
  worker. Данные не мигрируют — кеш и миниатюры производные, их потеря
  безопасна.
- Уже загруженные вложения с неготовой миниатюрой чинятся сами: очередь `media`
  доготовит их, а лента подхватит при следующем открытии.
