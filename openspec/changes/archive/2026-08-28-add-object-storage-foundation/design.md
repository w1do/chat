## Context

Мотивация — в `proposal.md`, требования — в `specs/`. Ниже то, что определяет
подход; проверено по коду.

- MinIO объявлен в `infra/compose/compose.dev.yaml` и `compose.prod.yaml` под
  профилем `s3`. В корневом `docker-compose.yml` его нет вовсе, в окружении
  контейнера `api` нет ни одной переменной `S3_*`/`AWS_*`, в `.env.example` —
  тоже.
- Диск `s3` в `apps/chat-api/config/filesystems.php` объявлен и читает пустые
  `AWS_*`.
- `spatie/laravel-medialibrary` не установлен ни в одном пакете.
- В `infra/docker/api/Dockerfile` ставятся `pcntl pdo_pgsql opcache intl zip
  bcmath`, `redis`, `gmp`. Ни `gd`, ни `imagick` нет.
- Готовность собрана из `ComponentCheck` (`DatabaseCheck`, `RedisCheck`,
  `QueueCheck`, `TcpCheck`, `HttpHealthCheck`) — место для проверки хранилища
  готово.
- `tools/chat` уже содержит группу `smoke` (`runtime`, `websocket`, `search`,
  `polza`) — дымовой проверке хранилища есть куда встать.

## Goals / Non-Goals

**Goals:**

- Хранилище есть у каждой установки, настраивается переменными и проверяется.
- Общие правила работы с медиа заданы один раз, а не в каждой функции заново.
- Готовность земли можно подтвердить до того, как появится первая функция.

**Non-Goals:**

- Не добавляется ни одной функции для человека: ни аватарок, ни вложений.
  Их несут `add-profile-and-room-images` и `add-message-attachments`.
- Не делается антивирусная проверка содержимого.
- Не делается загрузка напрямую в хранилище по подписанной ссылке.
- Не делается перенос уже существующих данных: хранить пока нечего.
- Не выбирается размер миниатюр и правила отдельных коллекций — это решает
  та функция, которой коллекция принадлежит.

## Decisions

### 1. Хранилище выходит из профиля в обязательные сервисы

Сервис объявляется без `profiles`, попадает в корневой `docker-compose.yml` и
в окружение контейнера `api`, переменные документируются в `.env.example`.

Это меняет обещание поставки: сегодня `CLAUDE.md` §14 называет хранилище
опциональным. Правка §14 и ADR обязательны — протаскивать такое молча нельзя,
иначе документация начнёт врать о составе установки.

Установка, где хранилище внешнее, ничего не теряет: сервис не поднимают,
переменные указывают наружу.

### 2. Отдельный диск с префиксами по назначению

Заводится закрытый диск поверх бакета `chat`. Внутри — префиксы по виду медиа:
`uploads/` для вложений, `avatars/` для аватарок, `rooms/` для фото комнат,
`wallpapers/` для обоев.

Префикс, а не отдельный бакет на каждый вид: один бакет проще создать,
забэкапить и объяснить, а по пути всё равно видно, что это за файл. Отдельные
бакеты понадобились бы только ради разных политик доступа, а политика здесь
одна — закрыто для всех, выдаёт приложение.

Видимость диска приватная. Публичный бакет сделал бы бессмысленной любую
проверку прав: адрес объекта угадывать не нужно, его достаточно один раз
увидеть.

### 3. Библиотека медиа подключается пакетами, а не приложением

`spatie/laravel-medialibrary` требуется тем пакетам, чьи модели владеют
файлами. Приложение регистрирует провайдер библиотеки и её миграцию, но не
знает о коллекциях: коллекция объявляется там же, где модель-владелец.

Здесь закладывается только общее: диск по умолчанию, очередь конверсий,
формат производных. Конкретные коллекции и размеры приходят с функциями.

### 4. Производные — webp, оригинал — по надобности

Все конверсии настраиваются на webp: он мельче при том же качестве, и это
прямо заданное требование.

А вот оригинал — вопрос, у которого два разных ответа, и смешивать их нельзя:

- Файл, который человек может захотеть скачать обратно (фотография во
  вложении), хранится **как прислан**. Пережать его в webp — необратимо
  испортить то, что отправили.
- Оформительская картинка (аватарка, фото комнаты, обои) назад не скачивается,
  её оригинал не нужен: хранится только webp нужных размеров.

Правило задаётся здесь, применяет его каждая функция для своей коллекции.

### 5. Конверсии — в своей очереди

Очередь конверсий отдельная от очередей переписки и уведомлений: пачка
загруженных изображений не должна задерживать живой разговор. Основная
операция завершается сразу, места, где нужна производная, показывают ожидание.

### 6. Расширение обработки изображений в образе

В образ добавляется то расширение, с которым библиотека медиа работает по
умолчанию, — без него конверсий нет вовсе, а значит нет и webp.

Берётся одно, а не оба доступных: второе тянет заметный вес ради возможностей,
которые продукту не нужны.

### 7. Бакет создаётся при установке идемпотентно

Создание бакета — часть запуска, а не инструкция администратору. Повторный
запуск на существующих данных ошибкой не заканчивается: «уже есть» — это
успех, а не сбой.

Альтернатива «создайте бакет руками в консоли» противоречит обещанию
«установка одной документированной командой».

### 8. Дымовая проверка — единственный способ доказать, что земля годна

У изменения-основы нет пользовательского сценария, которым его можно
проверить. Поэтому вводится команда, которая пишет объект, читает обратно,
сверяет и убирает за собой.

Без неё «хранилище настроено» подтверждалось бы только появлением первой
функции — то есть проверка уехала бы в чужое изменение. Команда остаётся
полезной и дальше: ею проверяют установку после обновления и смены ключей.

## Risks / Trade-offs

- [Обязательное хранилище ломает установки, поднятые без профиля `s3`] →
  в руководстве по обновлению описывается добавление сервиса и переменных;
  readiness сообщает о неготовности прямо, а не откладывает проблему.
- [Расширение обработки изображений утяжеляет образ] → плата за webp и
  миниатюры; без него ни одна из зависящих функций не работает.
- [Одна очередь конверсий на все виды медиа] → пока видов немного, этого
  достаточно; разделять есть смысл, когда появится измеримая помеха.
- [Изменение без пользовательской функции трудно приоритизировать] → дымовая
  проверка даёт ему собственный критерий готовности, а зависящие изменения
  явно на него ссылаются.
- [Префиксы в одном бакете вместо отдельных бакетов] → если однажды
  понадобятся разные политики доступа, разделение придётся делать переносом;
  сегодня политика одна, и разделение было бы преждевременным.

## Migration Plan

Схема базы прирастает таблицей библиотеки медиа; существующие таблицы не
меняются. Публичный контракт API не затрагивается — функций это изменение не
добавляет.

Для существующей установки порядок такой: добавить переменные хранилища,
поднять стек (сервис появится сам), выполнить миграции, запустить дымовую
проверку хранилища. Откат — возврат образа и compose-файла; данных, которые
можно потерять, на этом этапе ещё нет.
