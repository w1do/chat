## Purpose

Определяет единственный способ авторизации клиента чата: бессрочный
Sanctum-токен, выданный при входе, сохранённый клиентом и предъявляемый
заголовком `Authorization` в каждом запросе к API, real-time и защищённым
файлам, вместе с правилами его отзыва и поведением при отказе.

## Requirements

### Requirement: Вход выдаёт бессрочный токен доступа

Успешные `POST /auth/register` и `POST /auth/login` SHALL создать personal
access token предъявившего верные учётные данные пользователя и вернуть его
plaintext-значение в теле ответа рядом с прежним объектом пользователя. Токен
MUST быть создан без срока истечения и MUST оставаться действительным, пока не
отозван явной операцией. Каждый вход SHALL создавать отдельный токен, не трогая
токены, выданные ранее на других устройствах. Ответ MUST NOT устанавливать
cookie аутентификации.

#### Scenario: Успешная регистрация

- **WHEN** человек регистрируется с корректными логином и паролем
- **THEN** API отвечает `201`, телом отдаёт пользователя и plaintext-токен и не
  ставит ни одной cookie аутентификации

#### Scenario: Успешный вход

- **WHEN** человек отправляет верные логин и пароль
- **THEN** API отвечает `200`, телом отдаёт пользователя и новый
  plaintext-токен

#### Scenario: Неверные учётные данные

- **WHEN** пароль не подходит
- **THEN** API отвечает `401` в едином error envelope, токен не создаётся и в
  ответе его нет

#### Scenario: Токен не истекает сам

- **WHEN** с момента выдачи прошло больше любого прежнего срока сессии или
  cookie
- **THEN** тот же токен по-прежнему авторизует запрос, и повторный ввод логина
  и пароля не требуется

#### Scenario: Вход со второго устройства

- **WHEN** человек входит на втором устройстве
- **THEN** он получает отдельный токен, а первое устройство остаётся
  авторизованным своим

### Requirement: Клиент хранит токен и представляется им

Клиент SHALL сохранять полученный токен в `localStorage` и SHALL отправлять его
заголовком `Authorization: Bearer <token>` в каждом запросе к защищённым
эндпоинтам. Клиент MUST NOT полагаться на cookie: запросы к API MUST уходить
без `credentials` и без CSRF-заголовка. Токена нет — защищённый запрос MUST NOT
уходить в сеть вовсе.

#### Scenario: Запрос вошедшего человека

- **WHEN** приложение обращается к защищённому эндпоинту при сохранённом токене
- **THEN** запрос несёт заголовок `Authorization: Bearer <token>` и не несёт
  cookie аутентификации и `X-XSRF-TOKEN`

#### Scenario: Приложение открыто без токена

- **WHEN** в `localStorage` токена нет
- **THEN** защищённые запросы не отправляются, а человек видит форму входа

#### Scenario: Хранилище недоступно

- **WHEN** запись в `localStorage` невозможна (приватный режим, запрет политики)
- **THEN** приложение работает в пределах текущей вкладки и не падает, а после
  её закрытия требует вход заново

### Requirement: Вход переживает перезапуск браузера и сервера

Клиент SHALL восстанавливать текущего пользователя при старте единственным
запросом `GET /me` с сохранённым токеном. Восстановление MUST NOT зависеть от
серверного состояния сессии, кеша, Redis или установленной cookie.

#### Scenario: Перезапуск браузера

- **WHEN** браузер закрыт и открыт заново с сохранённым токеном
- **THEN** `GET /me` возвращает того же пользователя и чат открывается без
  ввода логина и пароля

#### Scenario: Перезапуск или очистка серверного состояния

- **WHEN** приложение и хранилище сессий на сервере перезапущены, а токен цел
- **THEN** `GET /me` по-прежнему возвращает того же пользователя

#### Scenario: Токен отозван

- **WHEN** сохранённый токен больше не существует на сервере
- **THEN** `GET /me` возвращает `401 unauthenticated`

### Requirement: Сессии и CSRF не участвуют в авторизации API

API MUST определять пользователя только по предъявленному токену. Запросы
`/api/v1/**` MUST NOT требовать cookie сессии, CSRF-handshake или заголовка
`X-XSRF-TOKEN`, и MUST NOT авторизовываться cookie-сессией браузера. Отсутствие
или недействительность cookie MUST NOT влиять на результат запроса с корректным
токеном.

#### Scenario: Мутация без CSRF-handshake

- **WHEN** клиент отправляет мутацию с корректным токеном и без всякого
  предварительного CSRF-запроса
- **THEN** API выполняет операцию и не отвечает `419`

#### Scenario: Запрос с посторонней cookie

- **WHEN** запрос приходит с корректным токеном и произвольной cookie сессии
- **THEN** пользователь определяется по токену, а cookie не влияет ни на
  identity, ни на права

#### Scenario: Запрос без токена

- **WHEN** защищённый эндпоинт вызван без заголовка `Authorization`
- **THEN** API отвечает `401 unauthenticated` в едином error envelope

### Requirement: Real-time авторизуется тем же токеном

Авторизация приватных и presence-каналов SHALL принимать тот же
`Authorization: Bearer <token>` и SHALL выдавать ровно те каналы, к которым
пользователь имеет доступ по HTTP. Отозванный токен MUST NOT авторизовать новую
подписку.

#### Scenario: Подписка на приватный канал

- **WHEN** клиент запрашивает авторизацию канала своей комнаты с действующим
  токеном
- **THEN** сервер выдаёт grant и события комнаты доходят до клиента

#### Scenario: Чужая комната

- **WHEN** клиент запрашивает канал комнаты, в которой не состоит
- **THEN** сервер отказывает и grant не выдаёт

#### Scenario: Токен отозван

- **WHEN** клиент пытается заново авторизовать канал после отзыва токена
- **THEN** сервер отвечает unauthenticated, а клиент прекращает попытки
  переподключения

### Requirement: Защищённые файлы доставляются авторизованным запросом

Изображения и файлы, отдаваемые защищёнными эндпоинтами (аватарки, фото комнат,
миниатюры и оригиналы вложений), SHALL запрашиваться клиентом с заголовком
`Authorization` и показываться из полученных данных. Права на файл MUST
проверяться сервером так же строго, как сейчас: доступ MUST NOT зависеть от
знания адреса. Адрес файла MUST оставаться неизменным между показами, чтобы
устройство переиспользовало уже загруженное изображение.

#### Scenario: Показ аватарки и миниатюры

- **WHEN** лента и список участников открываются у вошедшего человека
- **THEN** аватарки, фото комнат и миниатюры вложений отображаются

#### Scenario: Файл без права доступа

- **WHEN** запрошен файл вложения из комнаты, где человек не состоит
- **THEN** сервер отвечает отказом и содержимое файла не отдаётся

#### Scenario: Повторный показ того же изображения

- **WHEN** то же изображение показывается снова
- **THEN** оно берётся из кеша устройства, а не скачивается заново

#### Scenario: Изображение не загрузилось

- **WHEN** запрос изображения завершился ошибкой или отказом
- **THEN** на месте картинки показывается обычная замена (буква имени,
  заглушка), а экран не ломается и не уходит в повторы

### Requirement: Токен можно отозвать

Выход SHALL отзывать только токен текущего устройства и SHALL быть безопасным
при повторном вызове. Успешный сброс пароля SHALL отзывать все токены человека.
Смена пароля в настройках SHALL отзывать все токены человека, кроме того,
которым выполнен сам запрос. Отозванный токен MUST NOT авторизовать ни HTTP-, ни
channel-запрос.

#### Scenario: Выход

- **WHEN** вошедший человек вызывает выход
- **THEN** его текущий токен отозван, клиент стирает токен, и последующий
  `GET /me` с этим значением возвращает `401`

#### Scenario: Выход на одном из двух устройств

- **WHEN** человек выходит только на телефоне
- **THEN** токен телефона отозван, а компьютер остаётся авторизованным

#### Scenario: Сброс пароля

- **WHEN** пароль успешно сброшен по письму
- **THEN** ни один прежде выданный токен этого человека больше не авторизует
  запрос

#### Scenario: Смена пароля в настройках

- **WHEN** человек меняет пароль в настройках
- **THEN** текущее устройство продолжает работать, а остальные его токены
  отозваны

#### Scenario: Повторный выход

- **WHEN** выход вызван без действующего токена
- **THEN** ответ не содержит ошибки уровня сервера и ничего не восстанавливает

### Requirement: 401 после входа уводит на вход без мигания

Получив `401` по защищённому запросу при сохранённом токене, клиент SHALL один
раз перейти в состояние «вход недействителен»: стереть токен, остановить
real-time и очистить приватные данные устройства, после чего показать форму
входа. Пока это состояние не разрешено, дальнейшие защищённые запросы MUST NOT
уходить в сеть. Клиент MUST NOT предпринимать автоматических попыток
восстановления входа.

#### Scenario: Одновременные 401

- **WHEN** несколько параллельных запросов отвечают `401`
- **THEN** переход происходит один раз, повторы прекращаются и экран не мигает

#### Scenario: Уход на форму входа

- **WHEN** состояние «вход недействителен» наступило
- **THEN** токен удалён из хранилища, сокет отключён, приватный кеш изображений
  очищен, человек видит форму входа

#### Scenario: 401 до входа

- **WHEN** `401` приходит на экране входа или на странице приглашения, где
  токена ещё нет
- **THEN** экран остаётся на месте и ведёт себя как прежде: это обычное
  «человек не представился»

### Requirement: Токен не утекает за пределы клиента

Plaintext-токен MUST присутствовать только в теле ответов `/auth/login` и
`/auth/register` и в заголовке `Authorization` исходящих запросов. Он MUST NOT
появляться в адресах, query-параметрах, логах приложения и веб-сервера,
telemetry, отчётах об ошибках и любых других ответах API. Хранимое значение
токена в базе MUST оставаться хэшем.

#### Scenario: Адреса запросов

- **WHEN** клиент запрашивает данные или файл
- **THEN** значение токена отсутствует в пути и query-параметрах запроса

#### Scenario: Журналы

- **WHEN** запрос попадает в журнал приложения или ошибку
- **THEN** значение токена в записи отсутствует

#### Scenario: Профиль пользователя

- **WHEN** клиент запрашивает `GET /me` или другие данные пользователя
- **THEN** ответ не содержит plaintext-токена

### Requirement: Идентичность вычисляется на каждый запрос

Пользователь SHALL определяться заново для каждого HTTP- и channel-запроса по
предъявленному токену и MUST NOT сохраняться в изменяемом singleton- или
static-состоянии. Последовательные запросы разных пользователей к одному worker
MUST получать только свои данные.

#### Scenario: Два пользователя в одном worker

- **WHEN** один Octane worker подряд обслуживает запросы двух пользователей с
  разными токенами
- **THEN** каждый ответ содержит identity и данные только своего пользователя

#### Scenario: Запрос без токена после запроса с токеном

- **WHEN** сразу после авторизованного запроса тот же worker обслуживает запрос
  без заголовка `Authorization`
- **THEN** ответ — `401`, и данные прежнего пользователя не раскрываются
